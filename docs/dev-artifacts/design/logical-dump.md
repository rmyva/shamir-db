# Logical dump and restore design

**Status:** Proposed design. Sections 1 and 7 now record observed current-state evidence and consistency gaps; all other sections specify proposed behavior, not current implementation. New APIs, mechanisms, and visibility are proposals for a later implementation audit; this document does not assert that they exist.

## 0. Decisions (proposed)

1. **Treat a logical dump as a portable interchange artifact, not a physical backup.** It represents logical schema and selected database state; format versioning is independent of the on-disk storage-format epoch. Its purpose includes cross-machine transfer and recovery when an in-place format migration is unavailable. (Source: `docs/dev-artifacts/release-1/03-logical-dump-restore.md`, §§1–2, 4.)
2. **Start with one database, schema plus data, in canonical typed MessagePack.** The default scope is all repositories in that database. `--repo`, `--table`, and `--schema-only` are included as optional scope controls. Data-only, merge, and overwrite modes are deferred — a stated deviation from the release plan's selectivity and import-into-existing properties (`docs/dev-artifacts/release-1/03-logical-dump-restore.md` §3; open question 11). JSON is not part of this format; the release plan's line-delimited JSON alternative is R3c stage work with its explicit type caveats (`docs/dev-artifacts/release-1/03-logical-dump-restore.md` §§2, 5). (Source: same, §§2, 5; scope decisions proposed here.)
3. **Use a new server-wide maintenance gate for online export.** It blocks and drains writes, DDL, buffer expiry/maintenance, replication apply, and identity/ACL changes. Only after drain is logical instant *T* recorded and each included repository version *V_r* plus system/security state captured. The gate is held for the entire initial export (an explicit R3 deviation from the short online-backup barrier, pending a future snapshot primitive), with a 600-second maximum; timeout or cancellation releases it. This is new proposed functionality, not a claim about an existing online-backup snapshot. Offline CLI export instead requires exclusive ownership with no background mutation.
4. **Stream in bounded memory and reject over-limit input.** Do not materialize a table or whole artifact. Apply the limits in §3; external disk sorting may be used to produce canonical row order.
5. **Make the artifact self-describing and independently verifiable.** The required logical-dump format version and `required_features` determine compatibility. Source storage epoch and *T* are diagnostic only. The application-schema field is null at the R1c boundary; do not infer it. Include bounded section inventory and checksums as specified in §3.
6. **Load definitions before records and derived structures after records.** Compile/admit functions before bindings; suspend validators/transforms while loading; build indexes and foreign-key state and run full validation after records. Full-text/vector indexes are rebuilt. Never export compiled native caches.
7. **Keep identity/security handling explicit and secret-free.** Capture selected logical identities and ACLs without credentials, tokens, tickets, or key material. Imported users/groups are disabled and passwordless; ACLs with unresolved owners require explicit mapping. Never grant privileges or administrator status implicitly.
8. **Use the query builder for import operations.** If it cannot preserve raw record keys, add a narrow new private loader adapter over the necessary engine table/transaction APIs; do not construct internal operation messages by hand. Import is atomic and limited to an absent or truly empty DATA DIRECTORY. (Source: same, §3; exact adapter/API availability remains pending research.)
9. **Do not design encryption in R3.** The unencrypted marker is explicit; a future R2c envelope wraps the entire stream. Add no encryption design or dependency here.
10. **Treat TTL as buffer configuration, not record expiry.** The observed per-table `ttl_ms` is a buffer setting; R3 exports that duration unchanged in the table buffer configuration, and buffer contents are re-derived on import. No per-record expiry is observed.

### 1.9 Seed exporter/importer

The seed is a constrained replication-seed format, not a full logical dump. Export is Unix-only, refuses the system repository, an existing output, and quarantined repositories; it prepares the seed and loads table catalogues (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:32-35,63-87,120-127`). It exports only auto-bound declarative schema validators and refuses code bindings/FK/transforms (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:143-155`); it inventories but excludes regular/unique/sorted/index2 descriptors (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:156-201`). It requires MVCC and writes bounded sorted raw-key/payload frames (16 MiB) (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:205-265`), exports interner entries with IDs (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:302-335`), checks source changes (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:336-357`), then emits a manifest with format/codec versions, requirements, source db/repo, lineage/history epoch/version, certified gap, schema hash, artifact ID, excluded index policy, tables, and files (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:358-377`; manifest fields: `crates/server/shamir-sync/src/sync/replication_seed/artifact/manifest.rs:8-25`).

Codec limits are frame 16 MiB, metadata 64 MiB, artifact 1 TiB, and chunk 64 MiB; nesting depth is 64 with trailing-data checks; referenced interner IDs are collected (`crates/server/shamir-sync/src/sync/replication_seed/artifact/encoding/codec.rs:13-16,26-31,41-53`; re-exported as `replication_seed::codec`). Install verifies a trusted digest and is Unix-only, creates/locks a target and checks the writer stamp gate, stages through `SeedImageWriter`, writes schemas after data, re-verifies, then publishes/registers a receipt (`crates/server/shamir-sync/src/sync/replication_seed/install/installer.rs:81-95,114-190`). `MaintenanceOpen` owns the offline lock/open sequence as noted in §1.8. The seed does not establish portable system/security state, general code-function portability, JSON/vector payload portability, or included index descriptors/index data: system is refused, code bindings are refused, and descriptors are excluded. These exclusions bound what the seed demonstrates; they are not limitations on the proposed R3 format.

## 2. Testable requirements

1. **One logical instant:** Exercise concurrent writes, DDL, buffer expiry/maintenance, replication apply, and identity/ACL changes during online export. Each must be blocked or drained by the proposed server-wide gate; after drain the export records *T*, the included *V_r* values, and system/security state from that boundary. Verify the freeze lasts until export completion and that cancellation and the 600-second timeout release it. Offline export must refuse to run without exclusive ownership and no background mutation.
2. **Canonical logical round trip:** Cover every supported portable schema, value, identity/ACL, and record kind. Export, import to an empty destination, and export again; compare canonical logical content, not container bytes. Normalize only the exclusions in §3. Verify per-table `ttl_ms` round-trips exactly. Derived indexes are checked by definitions and query results, not internal bytes. Run the cycle a second time from the imported database (import, export, import) to prove the normalization is stable.
3. **Cross-format portability:** Import the R1b old-binary-export reference fixture on the supported newer importer without relying on the source storage layout. Treat source epoch as diagnostic and reject unsupported required format versions/features.
4. **Bounded-memory streaming and limits:** Exercise the 64 MiB and 1 GiB datasets in §5. Verify no whole-table or whole-artifact buffering, bounded external sorting, all §3 parser limits, and rejection of an artifact over 1 TiB.
5. **Offline verification and corruption detection:** Verify without opening a database. Reject modified header/section/frame, bad checksum or digest, invalid inventory/counts, malformed or noncanonical values, truncation, trailing bytes, unsupported required features, and input mutation between preflight and import. Failure must precede publication.
6. **Secrets and authorization:** Decode every section and assert absence of credential hashes/salts, key material, session tickets, tokens, replication cursors, and lineage secrets. Test denied superuser or included-scope read/manage ACL checks. Verify imported identities are disabled/passwordless and unresolved ACL owners fail unless explicitly mapped; no implicit grants/admin role.
7. **Scope and portable definitions:** Verify default all-repository schema+data, `--repo`, `--table`, and `--schema-only` produce coherent references and preserve definition-before-record ordering. Verify functions are compiled/admitted before bindings, loading validators/transforms are suspended, post-load indexes/FKs/full validation run before publication, and full-text/vector indexes rebuild. After import, invoke every imported stored procedure and validator binding and assert the persisted `call_signature` matches the exported one and the call passes the runtime signature check (`crates/engine/shamir-db/src/shamir_db/shamir_db/db/function/invocation.rs:105`; release-plan R3b acceptance, `docs/dev-artifacts/release-1/03-logical-dump-restore.md` §5).
8. **TTL semantics:** Export the per-table buffer configuration's `ttl_ms` duration verbatim. Buffer contents are re-derived on import. There is no observed per-record expiry, so do not encode absolute expiry timestamps, omit records as expired, or apply frozen-clock comparison semantics.
9. **Atomic failure and retry:** Test cancellation/failure at every frame and validation/publication boundary, conflicting and non-empty destinations, complete-target retry with exact digest/options/receipt plus integrity check, refusal for any mismatch, fresh-stage restart after partial failure, and no record-level resume. A failed import must never expose a destination that appears complete.
10. **Platform publication and resource acceptance:** Run the CI matrix in §5 on Linux, macOS, and Windows. Exercise same-volume publication and the documented durability behavior on each; test progress on stderr or job status and cancellation between frames.

## 3. Container and encoding (proposed)

### 3.1 Stream framing

The unencrypted baseline is a single forward-readable stream. All fixed-width integers below are unsigned big-endian unless stated otherwise.

1. The preamble is eight magic bytes `SDBLDMP\n`, followed by `version:u16`, `flags:u16`, and `header_length:u32`.
2. `header_length` bytes are one canonical named-MessagePack header, followed by `SHA256(header_bytes)` (32 bytes). The header declares the required format version, `required_features`, source storage epoch (informational), nullable application-schema version (null at the R1c boundary), *T*, included repository versions *V_r*, scope/options, and bounded section inventory. Baseline flags are zero and the header explicitly says encryption is `none`. Unknown required features or nonzero unsupported flags fail closed.
3. The header is followed by frames. Each frame is `length:u32`, `payload:length bytes`, and `checksum:32 bytes`. Payload length is at most 16 MiB. The checksum is `SHA256(sequence:u64 || length:u32 || payload)`; sequence starts at zero for the first frame after the header and increments once per frame. Sequence is implicit in stream position, not an additional wire field. Payloads are canonical named MessagePack and carry section-start, item, or section-end records.
4. Section-start declares the section name and expected item count when known. Section-end records actual item count and a SHA-256 over the canonical item payload bytes in that section. Counts, order, and section digests must agree with the inventory and trailer. Section order is fixed: identities; database (including `settings`, among them `root_meta` and `fn_namespace_meta`, `crates/engine/shamir-db/src/shamir_db/system_store/settings.rs:14-53`); repositories; tables (including each table's buffer configuration, `ttl_ms` included); portable schemas; validators and functions; guest WASM modules; bindings; index descriptors; ACLs; records; end. Definitions precede records. The inventory lists the emitted sections in this order, including empty sections where applicable. Scope-filtered exports include only selected objects and coherent referenced definitions/security entries. Imported identity items are stored disabled and passwordless: the marker is serde-default and omitted when false, so pre-existing record bytes are unchanged.
5. The final trailer is itself a checksummed frame. Its payload contains totals for all preceding frames/items/sections, each section count and digest, byte count through the end of the preceding frame, and SHA-256 of the exact byte prefix from magic through the end of the preceding frame. The prefix digest excludes the trailer frame entirely, avoiding a circular hash. The trailer checksum covers its own sequence, length, and payload. EOF must immediately follow its checksum; trailing bytes are an error.

The header is at most 16 MiB. The aggregate decoded metadata (header, inventories, definitions, identities, and all non-record section items) is at most 64 MiB. Limits are also: 64 MiB maximum working buffer; nesting depth 64; 65,536 entries per container (a container is one `List`, `Set`, or `Map` value and one section's item inventory); and 1 TiB maximum complete artifact. A file-input preflight rejects an input whose size already exceeds 1 TiB before reading it; server-side streaming enforces the same ceiling from the trailer's declared totals before staging. Enforce lengths and aggregate limits before allocation. A single value/item that cannot fit in a legal frame is rejected. These are format limits, not current implementation measurements.

This framing is intentionally not the seed artifact's wire format: the seed is named-MessagePack frames behind bare big-endian length prefixes, with no magic, no version prefix, and no per-frame checksums; its integrity is file-level SHA-256 recorded in its manifest (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:257-259`; `crates/server/shamir-sync/src/sync/replication_seed/artifact/encoding/codec.rs:13-16`). The release plan requires that the seed, backup, and dump do not become three divergent codec implementations (`docs/dev-artifacts/release-1/03-logical-dump-restore.md` §4): the canonical named-MessagePack encode/decode helpers, the length/depth limits (deliberately identical: 16 MiB frame, 64 MiB metadata, 1 TiB artifact, 64 MiB chunks, depth 64), and the SHA-256 helpers are shared implementation; only the framing differs, because streaming verification of a single-file artifact needs per-frame checksums.

### 3.2 Canonical named MessagePack and logical values

Use named MessagePack maps with UTF-8 field names. Reject invalid UTF-8, duplicate map names, unknown mandatory fields, duplicate logical keys, noncanonical encodings, and values outside the declared limits. Canonical map fields and inventories are ordered by unsigned lexicographic order of their UTF-8 bytes; arrays retain logical order. Section and item encodings have one canonical representation.

Every database value uses an explicit tagged envelope, so format readers do not infer types from a host language. The observed `Value` kinds include `Null`, `Bool`, `Int(i64)`, `F64`, `Dec`, `Big`, `Str`, `Bin`, `List`, `Set`, and `Map` (`crates/foundation/shamir-types/src/types/value.rs:29-44`). Default serde encodes `Dec` and `Big` as strings, making them ambiguous with `Str` in plain MessagePack (`crates/foundation/shamir-types/src/types/value.rs:70-71`); therefore the envelope explicitly distinguishes `Dec`, `Big`, `Str`, and `Int` to prevent lossy or ambiguous round trips. Required tags also cover binary bytes, arrays, and maps. Integer envelopes carry an explicit width/type tag and fixed-width big-endian bytes (signed values use two's-complement); add `i128`/`u128` tags only when the logical model supports those types. Float envelopes carry an explicit width tag and the exact IEEE-754 bit pattern as 4 or 8 bytes, preserving signed zero and NaN payloads. Binary values remain bytes, arrays are ordered tagged values, and map keys are UTF-8 names sorted by bytes. The sorting rule applies to the format's own maps — header, inventory, section and item envelopes. Record payload `Map` and `Set` values are insertion-ordered in the database (`Value::Map(TMap)`/`Value::Set(TSet)`; `TMap`/`TSet` are `IndexMap`/`IndexSet` — `crates/foundation/shamir-types/src/types/value.rs:41-43`; `crates/foundation/shamir-types/src/types/basic/common.rs:5`) and are exported, imported, and compared in their stored iteration order: sorting their keys would silently reorder user data through a round trip and change an order clients can observe. Unsupported logical value kinds fail rather than being coerced or silently dropped. No native host IDs or interner IDs are encoded as field names.

Record items preserve the raw record key bytes and logical value; sort records by raw key bytes. Sort inventories by canonical logical name/key. Use bounded external disk sorting if the source cursor order is not canonical; never collect a whole table in memory. Section digests and the trailer provide corruption detection only, not authentication. The artifact contains no secrets and has no encryption/authentication claim.

### 3.3 Portable content and exclusions

Include portable schema, function source/definitions, guest-module bindings, index descriptors, logical records and keys, and selected identity/ACL metadata. The offline export preserves stored-shape fidelity for strings and arrays: the storage codec flattens `Dec`/`Big` to strings and `Set` to lists, so the export emits what is stored — a stored string as `str`, a stored list as `list`, recursively inside nested maps and lists — and the artifact round-trips the stored bytes exactly; the import accepts every envelope tag, so a future exporter that tags `dec`/`big`/`set` needs no import change. Functions carry their stored `version` and `call_signature` (`crates/engine/shamir-db/src/shamir_db/shamir_db/db/function/management.rs:246-248,266-267`) and their `FunctionMeta` (visibility, Invoker/Definer security, secret and network grants; `crates/wasm/shamir-wasm-host/src/builtin/meta.rs:79-95`); declarative validator entries and function folders belong to the same functions content (`crates/engine/shamir-db/src/shamir_db/system_store/validators.rs:12-213`). Full-text/vector index state is derived and rebuilt. Compiled native caches and native module hashes are never exported. Source is recompiled on import. A recompiled module is equal when it exposes the same exported ABI and its persisted `call_signature` matches the exported one — the invocation path compares the persisted binary signature (`crates/engine/shamir-db/src/shamir_db/shamir_db/db/function/invocation.rs:105`); the raw module hash may differ across compiler versions and is excluded from equality. A source-less guest WASM module must include its portable WASM payload and be re-admitted; fail if the importer cannot support it. `--include-artifacts` may include additional raw guest artifacts only, never native caches. Unsupported or unadmittable required guest modules fail import.

Never include user credential material — the directory's `salt`, `stored_key`, `server_key`, and `kdf_params` (`crates/server/shamir-server-security/src/security/user_directory/record.rs:66-111`) — nor session tickets, consumed-ticket counters, the token store (`api_tokens`, `crates/server/shamir-server-security/src/security/tokens/store.rs:7,55-63`), the retired system-store `users`/`roles` tables (the users loader contract still attests `password_hash`, `crates/engine/shamir-db/src/shamir_db/system_store/identities.rs:90-103`; the `roles` table is created empty, `crates/engine/shamir-db/src/shamir_db/system_store/store.rs:33`), replication cursors, or lineage secrets. Source identity IDs resolve through stable logical user/group names; imported identities are disabled and passwordless. ACL owner references that cannot be resolved require an explicit mapping, otherwise import fails. No implicit grant or administrator assignment is made. Imported databases receive a new lineage; provenance is limited to nonsecret diagnostics. Replication configuration (`replication_profiles`, `publications`, `subscriptions`; `crates/engine/shamir-db/src/shamir_db/system_store/store.rs:51-58`) is not exported: an imported database starts unreplicated with its new lineage, and this exclusion is stated so the result is a complete copy of the exported scope.

The per-table buffer configuration's `ttl_ms` duration (`ALTER TABLE ... SET buffer.ttl_ms`; `crates/engine/shamir-db/src/shamir_db/execute/admin_meta/admin_buffer.rs:13-118`) is exported verbatim in the tables section's buffer-configuration fields; buffer contents are re-derived on import. The observed TTL is only this buffer knob, not per-record expiry, so there are no expiry timestamps to translate and no records to omit as expired. Canonical content equality excludes creation/export times, source versions *V_r*, physical IDs, interner IDs, new lineage, native module hashes, and disabled credential state. It includes every portable logical field, record key, and function `call_signature`; it must not mask semantic changes to compiled signatures.

## 4. Export and import protocol (proposed)

### 4.1 Export

- **Scope and entry points:** Export one database and, by default, all its repositories with schema and data. `--repo` and `--table` optionally narrow scope (`--table` resolves within a named repository); `--schema-only` omits records while retaining selected definitions and coherent references. Data-only, merge, and overwrite modes are deferred. Planned entry points are an offline export CLI and a server administrator export job; neither is asserted to exist.
- **Consistency:** Online export acquires the new server-wide maintenance gate. It blocks and drains every server write, DDL, buffer expiry/maintenance, replication apply, and identity/ACL change. Once drained, it records *T*, all included *V_r*, and system/security state, then holds the freeze through the complete export. The initial design intentionally accepts this long freeze instead of claiming reuse of a short online-backup barrier; a future snapshot primitive may remove that deviation. The online gate has a 600-second maximum; timeout/cancel aborts the artifact and releases the gate. Offline CLI export requires exclusive database/server ownership and no background mutation for its full duration. The header's source storage epoch comes from the format-stamp observation: online export reads the launcher-held stamp outcome (`docs/dev-artifacts/design/format-stamp.md` §5.1); offline export performs an Inspect-mode stamp check at open and refuses directories whose stamp is newer or older than the binary, exactly like seed export today (`crates/server/shamir-sync/src/sync/replication_seed/export/maintenance_open.rs:21-25`; `docs/dev-artifacts/design/format-stamp.md` §3.4 rows 8-12), because the offline open runs seed-style engine initialization, which performs WAL-recovery writes. A stampless or adopted directory records `unstamped` diagnostics instead of an epoch. A read-only engine open that would lift the offline refusal is the R3 prerequisite named by the stamp design (open question 12).
- **Authorization and output:** Require superuser authorization and verify every applicable read/manage ACL for all included objects/security state; any denial aborts. The server never accepts an arbitrary output path: it writes only under a configured private export root and returns an opaque job artifact path. Offline CLI output is caller-selected. Progress is written to CLI stderr or exposed as server job status. Cancellation is observed between frames, releases any online gate, and leaves no successful artifact.
- **Write format:** Build bounded header/inventory, stream selected definitions and records in §3 order, canonicalize ordering with bounded buffers or external disk sort, and write/check every frame. The artifact is complete only after the trailer and EOF have been written and verified. No secret material is emitted. The artifact is written under a unique temporary name in the export root and renamed to its final name only after trailer verification; an existing final name is never replaced, so a crashed export never publishes a partial artifact under a final name.

### 4.2 Import

- **Target and options:** Import only into an absent or truly empty DATA DIRECTORY; the importer's ownership lock lives beside the target (`<data_dir>.import.lock`), never inside it, so publication is a single same-volume no-replace rename of the stage onto the absent target path, and a directory containing any other entry is refused. Acquire exclusive ownership before inspecting or changing the target. `--as-db` consistently maps the artifact's database/repository/table references to the requested database name. Existing data is never merged or overwritten. Data-only, merge, and overwrite are deferred. Planned import is offline CLI; no server arbitrary-path import is proposed. The empty-target-only first cut is a stated deviation from the release plan's import-into-existing property with explicit conflict behavior (`docs/dev-artifacts/release-1/03-logical-dump-restore.md` §3); see open question 11.
- **Preflight:** Stream-verify the entire input before staging: magic/version/features, canonical encodings, limits, frame and section checksums/counts, trailer prefix digest, EOF, schema/reference coherence, and content digest. Reject secrets or unsupported required content. No database mutation occurs during preflight. Re-read and hash the exact input while loading; if it differs from the preflight digest, abort and discard the stage.
- **Stage and load:** Create a uniquely named sibling stage with create-new semantics on the same volume, owned by this import attempt. Load through query-builder batches. Add a narrow new private raw-key-preserving loader adapter over engine table/transaction APIs only if the query builder cannot preserve record keys; that adapter is new proposed work, not an existing capability claim. Load definitions before records; compile/admit functions before bindings; suspend validators/transforms during record load; rebuild indexes/FKs and run full validation after records. Restore identities disabled/passwordless (created via `insert_disabled_import` with CSPRNG salt/stored/server key material and default KDF params, refused on every authentication path like an unknown user, resolvable for ownership mapping, and left disabled until an operator provisions credentials), resolve ACL owners only through explicit mappings, and never add implicit grants/admin roles. Rebuild full-text/vector indexes.
- **Validation and publication:** Verify loaded logical content and artifact digest; flush and close the staged database; stamp its current storage-format epoch and a receipt containing exact artifact digest, effective options/mappings, and integrity information. Only then publish by same-volume atomic no-replace rename. Never replace existing data. A platform unable to provide the required no-replace publication must fail closed. Durability uses the platform-specific flush/readback path: the staged database is flushed and read back before the rename; the published rename itself is NOT followed by a sync of the parent directory in the current implementation (`stage/dir.rs`), so the published directory NAME has a residual power-loss risk on every platform, and Windows file-sync/readback has its own residual risk. Syncing the parent directory after the rename where the platform supports it is required by this design and is tracked as follow-up task #2056 (it is not done yet; do not claim power-loss durability of the published name). No extra dependency is assumed.
- **Retry and cancellation:** A complete existing target is accepted as an idempotent retry only when its receipt matches the exact artifact digest and effective options and an integrity check succeeds; otherwise refuse. A partial stage is not resumed: discard/recover only the attempt-owned stage and start a fresh one. Never resume at record level. Cancellation is checked between frames; before publication it discards the stage, and after successful publication reports success. Progress is stderr/job status as applicable. A stage left behind by a crashed attempt — a sibling matching this importer's unique stage-name pattern — is removed only while this attempt holds exclusive ownership, before the fresh stage is created.

## 5. CI-only tests and budgets (proposed)

These are CI acceptance tests and proposed budgets, not measurements or local test/build instructions.

- **Fixture matrix:** Small fixture covering all supported logical kinds and every optional scope; 64 MiB and 1 GiB streaming datasets; exact `ttl_ms` round-trip; identity/ACL mappings; source-less guest WASM and optional raw guest artifact. Include an R1b old-binary-export reference fixture. Run the format/round-trip/verification matrix on Linux, macOS, and Windows.
- **Positive cases:** Canonical export determinism for unchanged logical input, modulo the header's diagnostic fields (snapshot instant *T*, per-repository versions *V_r*, epoch observation) — frames after the header are byte-identical across repeated exports of the same frozen state; logical round-trip equivalence under §3 normalization; schema-only and selective scope coherence; verify-only operation; older-epoch fixture import; index rebuild/query checks; complete-target exact retry.
- **Negative cases:** All corruption, truncation, trailing data, over-limit, unsupported-feature, malformed/noncanonical value, changed-input, secret-absence, unauthorized-scope, unresolved ACL, unsupported guest module, non-empty/conflicting target, cancellation, gate-blocking/drain/timeout/release, partial-stage, and wrong-receipt cases from §§2–4. Assert no failed import publishes a destination and no canceled online export retains the gate.
- **Resource budgets:** On the 64 MiB dataset, each export, import, and verify operation completes within 60 seconds, excluding builds and index compilation; allow a separate index build/validation budget of 180 seconds. Workspace incremental RSS is at most 256 MiB above the open-database baseline, with backend RSS measured and reported separately. Check both datasets for bounded streaming and the 1 TiB parser limit without allocating an over-limit artifact in memory. The 1 GiB dataset runs under the same RSS cap with a generous fixed per-operation budget (600 seconds, excluding builds and index compilation), so a regression fails the test instead of hanging. Measured on the first enabled three-OS run after the batched-load fix (fork dispatch of 2026-11-26): the 1 GiB import (112 640 records, 224 transactions bounded by 512 records or 32 MiB of encoded rows) took about 120 s on Linux, 175 s on macOS and 275 s on Windows end to end (preflight 16/33/49 s, load 83/109/170 s, validation 16/30/53 s, receipt hash about 1 s); before the fix it did not finish in 3000 s because of one commit per record and a full-keyspace walk in every upsert pre-read. Building the 1 GiB fixture (241/495/700 s) and exporting it (54/172/178 s) are outside this budget and are tracked separately (task #2047).
- **Artifact-size assertion:** Assert framing/checksum overhead of at most 36 bytes per item frame (4-byte length plus 32-byte checksum), plus bounded fixed section/trailer framing, excluding payload and metadata. Do not impose a magic throughput or compression ratio assertion.

## 7. Current-code evidence

1. **No observed global snapshot:** the read API is per-table/repository MVCC and can be unavailable without an `MvccStore`; seed source-change detection does not provide one cross-repository/security boundary (`crates/engine/shamir-engine/src/table/table_manager/admission/views/read_only_views.rs:412-423`; `crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:205-206,336-357`).
2. **Seed is not a full logical dump:** it refuses the system repository, exports only declarative validator bindings, and inventories but excludes index descriptors and index data; it does not establish security/system export, JSON/vector payload portability, or general full-function portability (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:63-65,143-201`). Treat these as R3 coverage requirements, not as missing behavior promised by the seed.
3. **Seed carries interner IDs:** the existing seed pages/export interner IDs, whereas R3 intentionally uses logical field names (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:302-335`; R3 proposal §3.2).
4. **Seed platform limitation:** export and install are Unix-only; R3 needs its own cross-platform publication/durability design (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:32-35`; `crates/server/shamir-sync/src/sync/replication_seed/install/installer.rs:81-95`).
5. **Legacy system users contain `password_hash`:** this is separate from the server user-directory's persisted key/KDF model and must not be mistaken for a credential-free identity export (`crates/engine/shamir-db/src/shamir_db/system_store/identities.rs:90-103`; server representation: `crates/server/shamir-server-security/src/security/user_directory/record.rs:66-111`).
6. **TTL is only an observed buffer knob:** `ttl_ms` configures the per-table memory buffer; it is persisted as table buffer configuration (`crates/storage/shamir-storage/src/stores/storage_membuffer/core.rs:33-54`; `crates/engine/shamir-engine/src/table/support/model/buffer_config.rs:1-63`; DDL: `crates/engine/shamir-db/src/shamir_db/execute/admin_meta/admin_buffer.rs:13-118`). R3 carries the duration verbatim and re-derives buffer contents.
7. **No per-record expiry is observed:** do not export absolute expiry timestamps, omit records based on such timestamps, or add frozen-clock expiry semantics. This is distinct from the configured `ttl_ms` buffer duration (`crates/storage/shamir-storage/src/stores/storage_membuffer/core.rs:33-54`; `crates/engine/shamir-engine/src/table/support/model/buffer_config.rs:1-63`; `crates/engine/shamir-db/src/shamir_db/execute/admin_meta/admin_buffer.rs:13-118`).
8. **R3 staging must address the seed installer's empty-target/lock/stamp pattern:** the existing installer creates/locks the target, checks a writer stamp gate, stages a `SeedImageWriter`, re-verifies, and publishes; this is an analogy to audit, not an existing R3 facility (`crates/server/shamir-sync/src/sync/replication_seed/install/installer.rs:114-190`).
9. **Plain serde string ambiguity:** `Dec` and `Big` serialize as strings, so an untagged/plain MessagePack representation is ambiguous with `Str`; R3 must tag `Dec`, `Big`, `Str`, and `Int` explicitly (`crates/foundation/shamir-types/src/types/value.rs:29-44,70-71`).
10. **Retention audit item:** `admin_retention` is an admin surface, but its semantics are not verified; audit before making any retention claim (`crates/engine/shamir-db/src/shamir_db/execute/`).

## 8. Owner questions and defaults

Defaults below are resolved proposed behavior for this design; they do not claim implementation or require owner confirmation here.

1. **Version history and deleted records:** No; export only live logical state at *T*.
2. **Field names:** Export UTF-8 logical names; never depend on field-name interner IDs. Unlike this R3 default, the existing SEED-2 format carries interner IDs (`crates/server/shamir-sync/src/sync/replication_seed/export/exporter.rs:302-335`); this is a stated format difference, not an oversight.
3. **TTL:** Export per-table buffer `ttl_ms` duration verbatim; buffer contents are re-derived on import. No per-record expiry is observed, so the release-doc absolute-versus-remainder question dissolves: no per-record TTL exists to translate.
4. **Identities and authorization:** Include selected logical identities and ACLs, never credentials/secrets/tokens. Imported users/groups are disabled and passwordless. Require explicit mapping for unresolved ACL owners; no implicit grants or admin status.
5. **Destination and conflicts:** Import only to an absent or truly empty DATA DIRECTORY (allowing the importer's own lock); stage and publish atomically without replacing data. Exact complete-target retry only with matching digest/options/receipt and integrity check. No merge or overwrite.
6. **Scope:** Default one database, all repositories, schema plus data. Optional `--repo`, `--table`, and `--schema-only`; data-only is deferred. `--as-db` consistently maps logical references.
7. **Compiled artifacts:** Never export native caches. Recompile source. Include source-less guest WASM when required for portability; optional `--include-artifacts` covers additional raw guest artifacts only.
8. **Consistency and duration:** Online export uses a new server-wide maintenance gate held for the full export, maximum 600 seconds; offline export requires exclusive ownership and no background mutation.
9. **Encryption and dependencies:** Baseline is unencrypted; future R2c wraps the entire stream. Add no dependencies. Platform publication must fail closed when atomic no-replace semantics are unavailable; Windows file-sync/readback retains a residual power-loss risk.
10. **R1c application-schema journal:** the header's application-schema field is null until R1c exists; when it lands, the dump must carry the application-schema version (`docs/dev-artifacts/release-1/01-versioning-and-migrations.md` §5) and define the fate of the in-database migration journal (`docs/dev-artifacts/release-1/01-versioning-and-migrations.md` §4.1), because an imported database that claims a schema version but has an empty journal fails later migrations' checksum verification (`docs/dev-artifacts/release-1/01-versioning-and-migrations.md` §4.2). Default until the owner decides: import refuses any artifact whose application-schema field is non-null (fail closed); the R1c-aware design then either exports the journal rows with the dump or defines a synthetic base.
11. **Import into an existing database and data-only scope (stated deviations):** the release plan (`docs/dev-artifacts/release-1/03-logical-dump-restore.md` §3) lists import under another name, import into an existing database with explicit conflict behavior, and data-only selectivity; this design's first cut imports only into an absent or truly empty data directory and offers schema-only but not data-only. Default: keep the empty-target-only first cut and record the deviation; object-level conflict modes (refuse/skip/replace) for import-into-existing and data-only scope are follow-up work in the same format.
12. **Older-epoch export:** export of a directory whose format stamp is older or newer than the binary is refused, exactly like seed export today (`crates/server/shamir-sync/src/sync/replication_seed/export/maintenance_open.rs:21-25`; `docs/dev-artifacts/design/format-stamp.md` §3.4 rows 8-12), because the offline open runs WAL-recovery writes; a read-only engine open is the R3 prerequisite that would lift this (`docs/dev-artifacts/design/format-stamp.md` Q9). Default: refuse until that prerequisite exists; the cross-binary path remains export-with-the-old-binary (`docs/dev-artifacts/release-1/01-versioning-and-migrations.md` §3.8).
