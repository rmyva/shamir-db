# Wire keyword dictionary: strict numeric keys for OQL and DDL on the binary wire

Status: design, 2026-11-26, revised the same day and again after the independent review (section 7 lists what that review changed). Owner decisions: (1) "the keywords of OQL and DDL travel as numbers, from a hard-coded dictionary of their own, separate from the data interner"; (2) the switch is STRICT: old string keys are not supported, and it happens before the first release (after the release it would break deployed clients). Task #2026 measured the effect (section 4); it does not gate the work.

## 1. Problem

Every request and reply on the binary transports (TCP, WebSocket, Unix socket) is MessagePack produced by `rmp_serde::to_vec_named`: every struct field key and every enum variant name of the query DTOs travels as a string and is matched as a string on the other side.

Facts on `origin/master` (2026-11-26):

- `crates/query/shamir-query-types` declares about 530 distinct field names and about 500 variant names; `BatchOp` alone has 108 variants.
- 261 derived and 18 hand-written serde impls in that crate; 233 types are reachable from `DbRequest` and `DbResponse` (inventory of WIRE-DICT-1: 182 snapshot entries are marked indexable by a serializer adapter and 51 are marked non-indexed, see 3.4; the marks are an inventory, not a proof of coverage).
- 136 `#[serde(deny_unknown_fields)]` sites.
- The same DTOs are also deserialized from `QueryValue` trees inside the process (the WASM bridge, `ops/batch/ops/query_value_deserializer.rs`, `read/filter/filter_value.rs`), where keys are strings. That is not the binary wire and stays as it is.
- The same DTOs are also persisted (catalogue rows, migration journal, migration plans), serialized to JSON on HTTP JSON endpoints and the shell's printed forms, and handed across the napi boundary as NAMED MessagePack (not JSON; `repl(Buffer)` included). Those forms stay named.
- The data plane is separate: user field names in records are already interned to `u64` by the data interner; the ALIAS keys of `BatchRequest.queries` are user-chosen strings and stay strings.

## 2. Goal and non-goals

Goal: on the binary wire, every OQL and DDL keyword (struct field key, enum variant identifier, including the variant of a unit-variant enum VALUE such as an isolation level) of a request and of a reply is a small integer from a fixed dictionary, decoded without a string comparison. In the end state the server and every client accept ONLY that form: a string keyword is a typed protocol error.

Non-goals: the data plane (record field names, values, aliases), compression, the JSON surfaces (HTTP JSON endpoints, logs, the shell's printed forms), the napi JS-to-Rust boundary (named MessagePack), the persisted formats (migration journal, catalogue durability), the WASM gateway, the canonical HMAC bytes, the replication event and seed blobs (their own versioned encoder), the in-process `QueryValue` bridge. They keep serializing the same DTOs the way they do today. One decision is an explicit exception to "every keyword is a number": string-valued DSL spellings are VALUES of fields, not Serde identifiers, and stay strings. The set is ENUMERATED, not open-ended: `FieldRuleDto.type` and `vector_metric` today; WIRE-DICT-2 pins the list in the snapshot (`string_dsl_values`) and every other value of an enum type (for example `FilterExprOp`) is a numeric variant index. The operand keywords `$query`, `$fn`, `$cond`, `$expr`, `$param` and `$ref` are NOT an exception: they travel as protocol-owned nodes (3.4).

Consequence of strictness: all clients (Rust, the shell, the napi binding, the TypeScript client) and the server must switch in the same release. To keep `master` working at every step the rollout (section 6) adds the numeric form first with the server still accepting both, and the LAST step removes the named decoder and the named replies (numeric messages are strict from the first step that accepts them, 3.3). Not supporting the old form is the end state, not a day-one flag.

## 3. Design

### 3.1 Two dictionaries

- **Data interner** (exists): dynamic, per database, user field names to `u64`.
- **Protocol dictionary** (new): static, compiled into server and clients, never negotiated per session. It assigns to every field of every wire struct, and to every variant of every wire enum, a number that is local to its type (like protobuf field tags). Numbers of different types are unrelated, so there is no global limit and no reserved range: each type has its own space, almost always below 128, which MessagePack encodes in one byte.

### 3.2 The number is the declaration index, pinned

serde accepts an integer instead of a field or variant name: the identifier visitors generated by `#[derive(Deserialize)]` implement `visit_u64`, mapping index `i` to the `i`-th entry of the generated field (or variant) list (`serde_derive-1.0.229/src/de/identifier.rs:367-402`). That list is the declaration order MINUS the fields with `skip_deserializing` and the fields with `flatten`, so later indices shift down; `rename`, `alias`, `rename_all`, `default`, `skip_serializing` and `skip_serializing_if` do not change it. An out-of-range integer is an `invalid_value` error for an enum and for a struct with `deny_unknown_fields`; a permissive struct (no `deny_unknown_fields`) maps an unknown index to its ignored-field sink exactly as it ignores an unknown name today; `#[serde(other)]` turns every out-of-range integer into that variant.

The dictionary therefore IS the declaration order, and it is pinned:

- A committed snapshot `docs/guide-docs/client-server-protocol-spec/wire-dictionary.json` (WIRE-DICT-1) lists, per wire type reachable from `DbRequest` and `DbResponse`, its fields and variants in declaration order, with the value type of every field as written (the type graph the TypeScript codec needs), the normalized serde attribute set, the effective wire name and the verdict of 3.4. WIRE-DICT-1 is an INVENTORY and a drift guard; it is not yet the codec contract.
- A unit test rebuilds that table from the source and fails on any difference other than an APPEND at the end of a type. Reordering, renaming, changing a field's type or removing something fails CI. A removal or reorder is a protocol version change and regenerates the snapshot deliberately. "Append-only" protects existing numbers; it does not make an old decoder accept a newly emitted field or variant, so a server is always deployed before the clients that emit an addition.

**The codec contract is the EFFECTIVE index list, pinned by WIRE-DICT-2 (review finding).** The serialization index (what the adapter writes) and the deserialization index (what the derived identifier visitor accepts) are the same only when the type has no `skip_serializing`, no `skip_deserializing`, no `flatten` and no `#[serde(other)]`: `skip_serializing` emits no `skip_field` callback, so the adapter's counter would fall behind; a field with only `skip_deserializing` can still emit one; enum serialization passes the ORIGINAL declaration index while the derived visitor numbers the filtered list; flatten serializes through a map and the flattened outer visitor collects numeric keys as buffered content instead of dispatching them. WIRE-DICT-1's snapshot shows that today no wire type carries `skip_serializing`, `skip_deserializing` or `other` and two carry `flatten` (`QueryEntry.op`, `FieldRuleDto.constraints`); WIRE-DICT-2 turns that into a test (a wire type that gains one of them without an explicit wire form fails it) and adds to the snapshot: the effective ids per payload and per variant, including the hand-written forms (`BatchOp`, `TableRef`, ...); the attributes `from`, `try_from`, `into` and `remote` (`FieldRuleDto` actually deserializes through `FieldRuleWire`, so its effective schema is that of the wire type); and the per-type `deny_unknown_fields` flag. Unknown numeric ids are rejected only by types with `deny_unknown_fields`; a permissive struct ignores them exactly as it ignores an unknown name today, and that behaviour is documented, not changed.

Explicit per-field tags survive reordering but need a generated or hand-written serde impl for every type; pinning the declaration order gets the same wire with no new serde code for the types that a serializer adapter can handle.

### 3.3 Encoding and strict decoding

**Encoder: an adapter on the wire codec only.** Serialization of the DTOs stays the derived (named) one everywhere else. The wire codec wraps the MessagePack serializer in an adapter (`IndexedKeys<S>`):

- `serialize_struct(name, _)`: the adapter counts fields; `serialize_field(key, v)` writes the current index instead of `key`; `skip_field(key)` (emitted by serde for `skip_serializing_if`) advances the counter without writing. The map length written by `serialize_struct` already excludes the skipped fields (derive computes it before the call, `serde_derive-1.0.229/src/ser.rs:341-365,1149-1158`), so no length is rewritten.
- `serialize_*_variant(_, index, _)`: writes `index` instead of the variant name, for unit variants too. Nothing exists to reuse: every variant method of `rmp-serde` 1.3.1 ignores `variant_index` and writes the NAME, in the named and in the compact mode (`encode.rs:675-761`), so the adapter overrides all of them.
- Everything else (values, maps with dynamic keys such as user data and aliases, sequences, bytes) passes through unchanged.

**Decoder: derived identifiers accept integers; strictness has two layers, and neither is a blanket wrapper.** The derived deserializers already decode the integer form (3.2). A wrapper over the MessagePack deserializer in the wire codec (`StrictIds`) rejects a string or byte-string where an IDENTIFIER is expected, and only there: `deserialize_identifier` accepts an unsigned integer (positive fixint, `uint8`, `uint16`, `uint32`, `uint64`; an out-of-range value follows the type's rule of 3.2), a string identifier is a typed protocol error, and string VALUES, user data and the alias keys of `BatchRequest.queries` are untouched. The wrapper must interpose on map and sequence seeds, struct, enum and variant access and the `visit_some`/newtype callbacks, or nested values escape it. It is applied only on the streaming (unbuffered) paths that the audit confirms.

The wrapper cannot reach inside serde's private buffers: a derived internally tagged, untagged or flatten decode first collects `Content` and replays it through `ContentDeserializer` / `ContentRefDeserializer` / `FlatMapDeserializer`, which never call the outer wrapper (`serde_derive-1.0.229/src/de/enum_internally.rs:49-60`, `enum_untagged.rs:44-57`, `struct_.rs:327-344`). Replayed FIELD keys do reach `visit_u64`, but a named keyword inside a buffer is accepted silently and a bare integer enum VALUE inside a buffer is not decodable (`ContentDeserializer::deserialize_enum` accepts a string or a one-entry map, `serde-1.0.229/src/private/de.rs:1420-1475`). Converting the internal tags does not remove all buffers: `FnCall` is a derived untagged choice that buffers its payload; `FnCall::Complex.args` is a `FilterValue`, whose HAND-WRITTEN decoder then reads from that buffer, and its `$expr` variant holds a `FilterExpr` whose `op` FIELD is an external unit enum: a buffered replay cannot read that enum value as a bare integer (`fn_call.rs:22-32`, `filter_value_decoder.rs:10-13,81-120`, `filter/filter_expr.rs:11-15,53-57`). The rule therefore is: **no derived untagged, flatten, internally tagged or adjacently tagged decode may remain on the wire path in the end state.** Every such type gets an explicit wire form with a hand-written STREAMING `Deserialize` (a visitor over `MapAccess` reading numeric keys, no `Content`). Boundary validation may keep a buffer only if it validates the COMPLETE grammar before the replay.

**The completeness gate is a lint over an effective wire codec graph, not an attribute count.** The snapshot records attributes on declared DTOs, not the call graph of their decoders; three real cases escape an attribute-only check: `Filter`'s `deserialize_with` calls a function-local untagged `StringOrSeq` (`filter_enum.rs:415-428`), the durability `with` helper calls a local untagged `Wire` (`durability_override.rs:28-45,67-72`), and `TableRef` reads map keys as `String` with none of the four flagged attributes (`table_ref.rs:71-89`). The first two are identifier-free, but a registered mirror could still call such a helper. WIRE-DICT-2 therefore builds ONE gate over an explicit graph that includes `deserialize_with`/`serialize_with`/`with` helpers, `from`/`try_from`/`into`, hand-written decoders, aliases and any additional wire roots, and it FAILS CLOSED on an unaudited hook: every hook is registered in a reviewed table that says either "identifier-free scalar or sequence buffering, allowed" or "replaced by an explicit streaming form". Today's attribute inventory is 15 `tag` types (13 internal, 2 adjacent), 7 `untagged` and 2 `flatten`; it seeds the table and does not bound it.

Shape rules pinned by the decoder: a unit variant is written as a bare unsigned integer (the streaming path accepts it, `rmp-serde-1.3.1/src/decode.rs:508-524,895-927`) and the decoder also accepts the one-entry map `{index: nil}` that serde itself accepts; a payload variant is a one-entry map `{index: payload}`; a struct is a MAP with numeric keys. A positional ARRAY at a struct site is a typed error: derived struct visitors accept `visit_seq` without visiting any identifier (`decode.rs:730-748`, `struct_.rs:70-95`), so the wrapper hands struct visitors an adapter whose `visit_seq` fails, and the same guard covers the STRUCT-VARIANT payload of an enum, which `rmp-serde` routes through its tuple path (`VariantAccess::struct_variant`, `decode.rs:1000-1005`). Oracles: a named identifier and a positional struct payload are rejected through plain struct access AND through enum struct-variant access.

**Two complete decoders, no "both forms" decoder.** The `named` decoder is the legacy one and is used only for messages whose root is named; the `numeric` decoder has `StrictIds` ON from the first step that accepts numeric messages and is the only decoder numeric messages see, so a numeric message that carries a named identifier anywhere is refused from day one, not at the last step. The last step REMOVES the named decoder and the named reply path; it does not turn strictness on.

Limits on decode (frame size, nesting, the existing caps) are unchanged.

### 3.4 What an adapter cannot index, and what each category needs

The adapter and the derived identifiers cover plain structs and externally tagged enums. The inventory of WIRE-DICT-1 marks 51 reachable types as non-indexed (counts from its snapshot; the mark is an inventory, not a coverage proof: the completeness test of 3.3 and the per-type tests of WIRE-DICT-2 are the proof):

| Category | Why a serializer adapter is not enough | Wire form to specify |
|---|---|---|
| Internally tagged enums: `DbRequest` (`tag = "op"`), `DbResponse` (`tag = "kind"`), `ReplRequest`, `ReplResponse`, `ActivityRow`, `ListOp`, `VisibilityState`, `VisibilityWait`, `Temporal`, `Pagination`, `SelectItem`, `SelectExpr`, `Filter` | the tag is a string key in a buffered map; the variant is chosen by matching that string | a wire-only EXTERNALLY tagged form: one map entry whose key is the variant index and whose value is the variant payload; the JSON and stored form stay internally tagged |
| Adjacently tagged: `SchemaMigrationAdminOp`, `SchemaMigrationOp` | the tag VALUE goes through `serialize_unit_variant` and `deserialize_enum`, so the adapter can index it, but the derived decode buffers the content; the keys `tag` and `content` are named | wire-only externally tagged form by default (the conversion is a simplification, not forced by the tag value); the spike confirms it |
| Untagged: `ResourceRef`, `GroupRef`, `FnCall`, `SelectExprValue`, `AggregateField`, `NumDto`; plus `FilterValue`, which has a hand-written decoder that reads buffered content when reached through `FnCall` | no identifier at all: the variant is chosen by trial over buffered content, which the strict wrapper cannot see; payload FIELD keys inside replay through `visit_u64`, named keys inside are accepted silently | an explicit wire form with a hand-written streaming decoder (3.3); where two shapes are ambiguous after indexing (`ResourceRef::Database` and `Function` both become `{0: string}`) an explicit tag |
| `flatten`: `QueryEntry.op`, `FieldRuleDto.constraints` | a flattened struct is serialized as a map with string keys and matched against buffered strings; an integer key never matches an inner field | a wire-only form that carries the flattened value as a normal field (for `QueryEntry`: an `op` field holding the `BatchOp` wire form) |
| Hand-written impls (12): `BatchOp`, `TableRef`, `QueryRecord`, `FilterValue`, `InsertedRecord`, `TransactionInfo`, `ListActivityReq`, `ListShapeStatsReq`, `ResetShapeStatsReq`, `RecordId`, `SecretString`, `QueryValue` | the wire shape lives in the impl | per type: emit and accept the index form (for `BatchOp`: one map entry, key = variant index, value = the operation DTO decoded directly, no `QueryValue` detour), or keep the type as it is when it carries user data (`QueryValue`, `QueryRecord`, `RecordId`) |

Facts from WIRE-DICT-1 and from the review that shape the table:

- Field KEYS survive a buffered context (the buffered `Content::U64` key replays through `visit_u64`, `serde-1.0.229/src/private/de.rs:1462-1475`) and a numeric variant MAP KEY replays too; what does not decode inside a buffer is a bare integer enum VALUE (`ContentDeserializer::deserialize_enum`, `private/de.rs:1429-1459`; the unbuffered `rmp-serde` path accepts it through its unit-variant fallback). Because `DbRequest` is internally tagged, EVERY payload of a request is buffered today. Converting the internally tagged enums to the externally tagged wire form removes that buffering from the main wire path; the explicit wire forms of the untagged types remove the rest (3.3).
- `BatchRequest.queries` keeps string ALIAS keys, then `QueryEntry` flattens a `BatchOp`. Today `BatchOp` serializes its DTO directly and deserializes `(String, QueryValue)` entries, picks the operation from named keys and replays the DTO through `QueryValueDeserializer` (`batch_op.rs:263-282,388-446`); it is NOT generally a single-entry variant map. The in-process bridge carries an integer unit VALUE (`Value::Int`) but cannot carry numeric-keyed maps (`QueryValue = Value<String>`). On the wire the hand-written `BatchOp` form decodes the operation DTO straight from the stream.

**Boundary table: which codec applies to which scope.** Strictness reaches every protocol-owned OQL or DDL structure even when it rides inside a value; literal data and explicitly versioned non-OQL formats are untouched.

| Scope | Codec in the end state |
|---|---|
| Typed DB bodies: `DbRequest`, `DbResponse` and every payload reachable from them | dictionary codec (numeric) |
| Protocol-owned structures that travel today as named `QueryValue` payloads: the `changes_since` reply (built as a named map in `QueryRecord::Direct` and reconstructed by the client into `ChangesSinceResponse`, `admin_retention.rs:238-258`, `client_ops.rs:198-214`), export receipts (`export_gate.rs:198-212`), schema-migration plans (`schema_migration/plan.rs:392-412`) | become TYPED DTOs of the dictionary (listed work items of WIRE-DICT-2); the persisted journal and catalogue forms of the same data stay named |
| Operand nodes inside write operands and record-shaped values: `$query`, `$fn` (with nested `$ref`), `$cond`, `$expr` and `$param` (recognised in `planner.rs:429-445,469-487`, `param_subst.rs:220-248`, `write_helpers.rs:71-85,118-135`; a named `$expr` carries named `op` and `args` and a string `FilterExprOp`) | protocol-owned nodes: on the wire each travels as a MessagePack EXTENSION value whose payload is the numerically coded typed node (the spike compares it with a marker-key map whose key is a negative integer, which no data map can carry); the boundary decodes the node and REBUILDS the unchanged in-process string-keyed `QueryValue` for the planner. A literal data map carrying a reserved `$` key on the wire is a typed protocol error, because today the planner would execute it: that is the bypass of the keyword gate that this row closes (authorization is a separate layer and is unchanged) |
| Application data: record fields, values, `queries` aliases | unchanged (data interner and plain strings) |
| Subscription pushes: `PushEnvelope.data` carries record, key and snapshot metadata and the reactive `BatchResponse` and error payloads (`payload.rs:14-66`, `bridge.rs:547-562`, `flow/reactive.rs:86-92,172-177`, `push_envelope.rs:21-38`), and the subscription `sub` and `error` grant | the protocol-owned metadata, the nested `BatchResponse`, the error payload and the grant are TYPED DTOs in the dictionary codec of the subscribing request, whose codec is captured BEFORE the bridge task is spawned (pushes can arrive before the ack); the outer push demux format stays stable during the rollout (`mux/reader.rs:43-84`); record data stays data |
| Replication `Hello` and `Pull`, and the `replication_status` payload (`admin_replication.rs:760-782`) | dictionary codec; `Hello` and `Pull` are INDEPENDENT round trips, each mirrors its own request, nothing is stored with a stream; `replication_status` becomes a typed DTO; the nested events blob and the seed blobs keep their own versioned encoder and the follower's decoder (`wire_source.rs:40-71`, `loop_body.rs:591`) |

**Preflight and replies.** The raw preflight (`wire_preflight.rs:20-47,65-75,123-127`) reads `String` keys and follows named `batch`, `queries` and `for_each` paths, so it cannot precede the numeric decoder unchanged. WIRE-DICT-2 acceptance: either a numeric preflight, or entry counting before duplicate collapse on the decoded form, with a test that a duplicate-key flood is still refused by the same cap. On the reply side, batch, cursor AND `GetRecord` accounting measure serialized bytes (`budget.rs:151-184`) and the main handler can return previously stashed bytes without re-encoding (`handler/core.rs:829-841`, `execute.rs:646-677`; the stash is per task, `byte_budget.rs:487-518`, `operator_state.rs:506-554`): every reply producer receives the IMMUTABLE request codec before any accounting, and sizing, stashing and emitting use ONE `encode_reply(codec, &DbResponse)`, so a size is never computed on the wrong bytes. The global delivery cache of Records and Keys pushes keys encoded bytes by commit, database, repo, change and mode (`deliver_cache.rs:24-29,47-86`, `bridge.rs:353-378`): the codec becomes part of that key, otherwise a numeric subscriber can hit bytes encoded for a named one.

### 3.5 Mechanism choice and the spike

Two ways to build the wire forms of 3.4, and the review kept A:

- **A. Adapter plus per-type wire forms.** The adapter indexes everything it can; each non-indexed type gets a hand-written or macro-assisted wire form. A declarative external mirror of an internally tagged enum is part of A, not a third design: a `macro_rules!` mirror generates conversions from a shared declaration or an explicit variant list, but cannot inspect an existing enum and strip its attributes.
- **B. A dedicated wire derive for every wire type.** A proc macro generates `WireSerialize`/`WireDeserialize` from the same declaration, independent of serde's attributes and internals; it re-implements a subset of serde semantics (rename, default, skip, flatten, untagged) for 233 types and needs a new macro crate.

Recommendation: A. It is NOT assumed: step WIRE-DICT-2a is a SPIKE that decides CORRECTNESS before cost. It builds the narrow version of A first and runs these oracles: `DbRequest::Execute` (the real name of the batch entry) with a nested filter and a create-table-with-index DDL entry; a `DbResponse::Batch` reply; `ResourceRef::Database` against `ResourceRef::Function` (both would be `{0: string}` if indexed per branch); the buffered `FnCall::Complex` -> `FilterValue` -> `FilterExpr` chain of 3.3; a real mixed reply that carries data AND keywords; a request refused by the existing cap with the numeric preflight; a bodyless HTTP `Ping` and a pre-body HTTP refusal; a mixed-codec push through the shared delivery cache; a write operand carrying a `$expr` node and a literal map with a reserved `$` key; TS strictness checked BEFORE key normalization (an integer key against a numeric-looking string key); raw bytes Rust-to-TS and TS-to-Rust in both directions. B is compared only on the same oracles, by lines of code, attributes touched and failure modes. The spike is not merged.

### 3.6 Versioning and rollout (no dual form in the end state)

**The body codec is NOT tied to the SCRAM handshake version** (review finding). The nine-element signed challenge of task SCRAM-PIN-ORDER already owns handshake version 2 on its own schedule; a client built with SCRAM v2 and before the dictionary still speaks named bodies, so "one shared version" would give "SCRAM v2 + named bodies" and "SCRAM v2 + numeric bodies" the same label. Moreover the version check is internal (`UnsupportedVersion`, the connection closes; no typed reply an unchanged client can read), resume carries no application codec field (`ResumeInit`, `ResumeOk`), and bearer REST and token WebSocket decode the same `DbRequest` without a full SCRAM exchange (`executor.rs:209-240`, `token_loop.rs:343-355`; REST bodies are `application/msgpack`, and even the synthetic HTTP `Ping` and early error bodies have explicit named encoders, `launcher.rs:167-182`). A handshake version cannot select the body codec on all those entry points.

**Decision: the body codec is self-identifying per complete DB body, and replies mirror it.**
- **Root grammar.** The root of a DB body is either (a) a NONEMPTY map whose keys are all strings (`named`), in any key order, or (b) a numeric root: exactly ONE entry `{variant_index: payload}`, where a root unit variant (`Ping`, `Pong`) is the entry `{index: nil}`; bare integer units exist only at nested sites. The codec is read from the first key marker after the map header, which for Map16 and Map32 means after reading the length. Mixed root keys, a non-map legacy alias, an empty map and a truncated header are typed protocol errors and are NEVER retried under the other codec.
- **Only complete inner DB bodies are sniffed.** Framing, authentication, the outer envelope, close and HTTP status errors stay codec-neutral: native TCP/IPC oversize frames that stop at the length header, malformed envelopes, session failures and rate limits already have outer-error or close paths (`framing.rs:135-153`, `request_loop.rs:293-303,347-366,384-415`), full SCRAM and resume are separate exchanges that feed the same post-auth loop, and WS upgrade refusals and HTTP auth gates, 413s and `GET /ping` run before any body exists (`service.rs:92-142,186-215,327-333`, `routes/ws/handler.rs:76-83`). There is NO "last good codec" fallback: on a multiplexed or pooled connection it is unrelated to the current request, and a synthesized `Ping` would only reveal the server's own codec.
- **Per-request selector for bodyless HTTP.** A bodyless HTTP request or an early HTTP reply that must carry a DB body takes its codec from the request header `X-Shamir-Body-Codec` (`named` or `numeric`); an absent header means `named` until the named path is removed and `numeric` after. Everything else on those paths is a fixed, codec-neutral status.
- **Token WS refusals are pinned separately:** a malformed body returns the outer `error` today and a policy denial may return an inner `DbResponse::Error` (`token_loop.rs:60-75,335-358,397-419`); the first stays codec-neutral, the second mirrors the sniffed request codec.
- **The reply is encoded with the codec of the request it answers**, through the one `encode_reply` of 3.4. Pushes use the codec captured from the subscribing request before the bridge task is spawned; replication calls mirror each request independently.
- **Dual mode** (steps 2 to 4): the server accepts both roots on every entry point, runs the `named` decoder for named roots and the strict `numeric` decoder for numeric roots, and mirrors each. **Final step:** the `named` decoder and every named reply path are removed; a named root is refused with a typed protocol error encoded `numeric`.
- **Whole codecs, server first:** the server learns both codecs and the mirrored reply path, then every consumer migrates, then named mode is removed. There is no mixing inside a message.
- **Legacy outcome per entry point after the final step** (replaces the earlier promise of a typed version error at the handshake): an old named client receives a numeric-encoded typed refusal; what it does with it is the OLD client's behaviour and is asserted as observed, not as a universal decode failure (the native TS mux checks `kind` conditionally and may resolve an unfamiliar decoded object, `client.ts:310-336`); REST answers HTTP 400 with a numeric body. Tests required in addition: a CURRENT client that sends a nested named identifier inside a numeric message gets the specified typed rejection, and the reciprocal client test where a named reply makes a current client fail with a typed error.
- `query_version` stays the query-language version it is today.

### 3.7 TypeScript client

`@msgpack/msgpack` encodes plain objects with string keys, and a JavaScript object cannot tell the integer key `0` from the string key `"0"`: the decoder of the numeric codec must read maps as `Map` (integer keys preserved) before any normalization, and the strictness check runs on that form; the current decoder delegates straight to the generic object decoder (`framing.ts:218-220`). The TS codec needs the dictionary AND the type graph (which DTO sits at which position, from the snapshot) to replace keys by indices and to map numeric replies back to named objects. A generated TS module carries the table; parity tests encode a shared corpus of requests in Rust and in TS and require identical bytes.

### 3.8 Debugging

Numeric frames are unreadable raw. The shell and a diagnostic decoder print them named through the dictionary (the snapshot has the names); the audit log and metrics keep their own names.

### 3.9 The flip checklist: live wire against local formats

Named mode is removed only when every LIVE consumer is on the numeric codec; local and named formats are kept. Live wire to migrate: the pure TypeScript client (named inner requests and replies today, `client.ts:310-350,420`), token HTTP and token WS, resume, `changes_since`, subscriptions (the reactive subscription e2e today asserts that an event ARRIVED, not that its nested response decodes: it must decode it), the Rust client, the shell TCP, IPC and token paths (raw shell probes migrate explicitly, `raw_scram.rs:392-402`, `transport.rs:323-340`), and the Rust network leg of the napi binding. ## 4. Effect: expected, and measured by #2026

Expected: each key shrinks from 1 + its length to 1 byte; decode becomes one integer jump per key instead of a string match; nothing changes for values and data.

Measured (task #2026, bench `crates/server/shamir-server/benches/wire_decode_measure.rs`): five builder-made requests, named encoding (`rmp_serde::to_vec_named`, the production form) against the positional "compact" form (`rmp_serde::to_vec`), which is a size comparison only (a numeric-keyed map still carries one key per field, and the compact probe is separate from the handler-success check, which used the named requests). Every scenario is executed once through the real handler on an in-memory database and its reply is checked BEFORE timing (`WIRE_DECODE_E2E_CHECK ok=true` for all five, in both runs). Two runs under `wnice -p idle -c 10 -t 8 -m 50` while other executors compiled on the same machine: the same cell differs by up to 2.9x between the runs, so read these as orders of magnitude. Times in microseconds, run 1 / run 2.

| Scenario | Request bytes named / compact | `decode_named` | `end_to_end` | Decode share of `end_to_end` |
|---|---|---|---|---|
| point read | 447 / 148 (3.0x) | 83 / 79 | 483 / 472 | 17% / 17% |
| single insert | 386 / 137 (2.8x) | 29 / 49 | 906 / 485 | 3% / 10% |
| batch of 1000 inserts | 73825 / 73576 (1.003x) | 48692 / 35386 | 1 iteration only: 30067 ms / 629 ms | not usable / 6% |
| nested filter and projection | 621 / 242 (2.6x) | 177 / 99 | 1875 / 1206 | 9% / 8% |
| DDL (create table, 3 indexes) | 756 / 507 (1.5x) | 91 / 165 | 701 / 776 | 13% / 21% |

Compact against named decode of the whole `queries` map (the largest part that round-trips in compact form): point read 78 -> 58 / 74 -> 28; nested filter 128 -> 109 / 185 -> 106; single insert, 1000-insert batch and DDL show no consistent gain (the differences are inside the noise, in both directions).

What the numbers support:

1. Bytes are the clear win: keyword overhead is 2.6-3.0x of the request for small reads, inserts and filtered reads, 1.5x for DDL, and nothing for data-heavy batches (1.003x).
2. CPU: decoding the whole request is 3-21% of the server-side time of a request, and the compact probe shows savings from none to about half of that decode, which says nothing certain about numeric keys. The CPU gain of the PROPOSED codec is UNMEASURED: compact positional bytes are a size comparison, not a lower bound for a codec that changes buffering and dispatch, and these cells do not support a ceiling such as "about 5%". The handler-success check of the bench used NAMED requests only (compact decoding is a separate probe). The re-measure of WIRE-DICT-5 compares named against numeric through the same typed-result oracle in CI.
3. The full-request compact form does not even round-trip (`BatchRequest.name` is `Option<String>` with `skip_serializing_if`, so every later position shifts). Positional encoding is not an alternative; numeric-keyed maps (this design) are.
4. The 1000-insert end-to-end cell ran one iteration and varied by a factor of 48; its share is not a result. Run it with more iterations in step WIRE-DICT-5, on a quiet machine.

The owner's decision does not depend on these numbers; they set the expectation: the gain is mostly in bytes of small requests, not in CPU.

## 5. Risks

- The scope is larger than "an adapter": the 51 non-indexed entries need explicit wire forms (the count is a mark, not a coverage proof), every derived buffered decode on the wire path has to go (3.3), `BatchOp` and the `queries` path change, the preflight and the reply sizing, stashing and emission change (3.4), and protocol-owned payloads that ride as named `QueryValue` become typed DTOs. The spike (3.5) exists to find out the cost before the real step.
- The strictness wrapper is only as good as the audit of the streaming paths: a type that regains `untagged`, `flatten` or a tag attribute reintroduces a buffer that accepts named keys silently; the completeness test of 3.3 is the guard.
- One documented exception to "everything numeric": the enumerated string-valued DSL spellings (section 2); it is the owner's to accept or overrule. Operand nodes (`$expr` and the others) are protocol-owned nodes with a boundary that rebuilds the in-process form (3.4); that boundary and the rejection of literal maps with a reserved `$` key are the riskiest new code of the step.
- A permissive struct (no `deny_unknown_fields`) ignores unknown numeric ids as it ignores unknown names; the snapshot carries the flag per type.
- A silent reorder of a wire type would mis-decode across versions: the snapshot test is the guard and runs in the fast tier; it compares field value types and attributes, not only names.
- `#[serde(other)]` turns every out-of-range integer into that variant, which hides a stale dictionary: such types keep a typed error instead (audited one by one).
- Removing named mode is a one-way step: every live consumer of 3.9 must be on the numeric codec before it, the TypeScript and napi live suites must be run by dispatch (normal CI does not run them), and the legacy outcomes of 3.6 must be tested against an old-protocol client fixture.
- The TS type graph must follow every DTO change: the parity test catches drift.
