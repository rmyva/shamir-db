# Wire keyword dictionary: numeric keys for OQL and DDL on the binary wire

Status: design, 2026-11-26. Owner request: "the keywords of OQL and DDL travel as numbers, from a hard-coded dictionary of their own, separate from the data interner". The measurement of task #2026 (`docs/dev-artifacts/prompts/perf/167-wire-decode-measure.md`) supplies the numbers of section 4; the owner decided on 2026-11-26 that the dictionary is built regardless.

## 1. Problem

Every request and reply on the binary transports (TCP, WebSocket, Unix socket) is MessagePack produced by `rmp_serde::to_vec_named`: every struct field key and every enum variant name of the query DTOs travels as a string and is matched as a string on the other side.

Facts on `origin/master` (2026-11-26):

- `crates/query/shamir-query-types` declares about 530 distinct field names and about 500 variant names; `BatchOp` alone has 108 variants.
- 261 derived and 18 hand-written serde impls in that crate. `BatchOp` (`ops/batch/ops/batch_op.rs`) is hand-written: a single-entry map whose key is the operation name (`"cancel_tx"`, ...).
- 136 `#[serde(deny_unknown_fields)]` sites.
- The same DTOs are also deserialized from `QueryValue` trees (the WASM bridge, `ops/batch/ops/query_value_deserializer.rs`, `read/filter/filter_value.rs`), where keys are strings and the deserializer reports `is_human_readable() == false`.
- The same DTOs are also persisted (catalogue rows, migration plans) and serialized to JSON at the napi boundary.
- The data plane is separate: user field names in records are already interned to `u64` by the data interner.

Cost of the strings: wire bytes (a key of 4-20 bytes where one byte would do) and a string match per key on decode. Both are per KEY of the request, so they grow with batch size and with keyword-heavy requests (filters, DDL), not with the size of the data.

## 2. Goal and non-goals

Goal: on the binary wire, every OQL/DDL keyword (struct field key, enum variant name) of a request and of a reply is a small integer from a fixed dictionary, decoded without any string comparison, while every other consumer of the same DTOs keeps working unchanged.

Non-goals: the data plane (record field names, values), compression, the JSON surfaces (napi, HTTP JSON endpoints, logs, the shell's printed forms), the persisted formats.

## 3. Design

### 3.1 Two dictionaries

- **Data interner** (exists): dynamic, per database, user field names to `u64`.
- **Protocol dictionary** (new): static, compiled into server and clients, never negotiated per session. It assigns to every field of every wire struct, and to every variant of every wire enum, a number that is local to its type (like protobuf field tags). Numbers of different types are unrelated, so there is no global limit and no reserved range: each type has its own space, almost always below 128, which MessagePack encodes in one byte.

### 3.2 The number is the declaration index, pinned

serde already accepts an integer instead of a field or variant name: the identifier visitors generated by `#[derive(Deserialize)]` implement `visit_u64`, mapping index `i` to the `i`-th (non-skipped) field or variant. So a decoder for numeric keys already exists in every derived DTO, at zero cost: an integer key is matched by a jump table, not by `memcmp`.

The dictionary therefore IS the declaration order, and it is pinned:

- A committed snapshot `docs/guide-docs/client-server-protocol-spec/wire-dictionary.json` lists, per wire type reachable from `DbRequest` and `DbResponse`, its fields and variants in index order.
- A unit test rebuilds that table from the code and fails on any difference other than an APPEND at the end of a type. Reordering, renaming or removing a field or variant of a wire type fails CI. A removal or reorder is a protocol version change and regenerates the snapshot deliberately.
- Round-trip tests per wire type: named encoding and indexed encoding decode to the same value, including types with `skip_serializing_if`, `default` and `rename`.

Explicit per-field tags (`#[wire(tag = N)]` through a derive macro) were considered: they survive reordering, but need generated serde impls for 260 types. Pinning the declaration order gets the same wire with no new serde code; explicit tags stay an option if churn ever demands it.

### 3.3 Encoding: an adapter on the wire codec only

Serialization stays the derived (named) one everywhere. The wire codec wraps the MessagePack serializer in an adapter (`IndexedKeys<S>`):

- `serialize_struct(name, _)`: the adapter counts fields; `serialize_field(key, v)` writes the current index instead of `key`; `skip_field(key)` (emitted by serde for `skip_serializing_if`) advances the counter without writing. The counted index equals the deserializer's index for every field that is not `#[serde(skip_serializing)]`-only; the snapshot test rejects that attribute on wire types.
- `serialize_*_variant(_, index, _)`: writes `index` instead of the variant name.
- Everything else (values, maps with dynamic keys such as user data, sequences, bytes) passes through unchanged.

Because only the wire codec uses the adapter, the persisted formats, the JSON surfaces and the `QueryValue` bridge do not change, and the `is_human_readable` switch is NOT used (the bridge already reports `false` with string keys, so that switch cannot carry this meaning).

### 3.4 Decoding: both forms, always

The decoder needs no adapter: derived identifiers accept a string or an integer. A server therefore accepts named and indexed requests at the same time; old clients keep working. Limits on decode (frame size, nesting, the existing caps) are unchanged.

### 3.5 What cannot use indices (audit, task WIRE-DICT-1)

- `#[serde(flatten)]` structs: serialized through `serialize_map` with string keys and deserialized through buffered content that matches strings. They keep names on the wire (the adapter leaves `serialize_map` keys alone).
- Internally tagged (`#[serde(tag = "...")]`) and untagged enums: the tag is matched as a string after buffering. They keep names, or are converted to externally tagged where the wire allows it.
- The 18 hand-written impls: converted one by one to emit and accept the index (for `BatchOp`, the hottest: emit `index => payload`, accept `index` or `name`), or left named with a reason.
The audit result is part of the snapshot: every wire type is marked `indexed` or `named` with the reason.

### 3.6 Negotiation and replies

Requests: no negotiation needed (3.4). Replies: the server encodes a reply indexed only when the request said the client understands it: a bump of `query_version` (already carried by every request) to a version that means "indexed replies". Older versions get named replies. The Rust client, the shell and the TypeScript client switch to indexed requests and the new version once they ship the dictionary.

### 3.7 TypeScript client

`@msgpack/msgpack` encodes plain objects with string keys. The TS codec needs the dictionary AND the type graph (which DTO sits at which position) to replace keys by indices and to map indexed replies back to named objects. Both come from the snapshot: it records, per field, the wire type of its value. A generated TS module carries the table; parity tests encode a shared corpus of requests in Rust and in TS and require identical bytes.

## 4. Effect: expected, and measured by #2026

Expected: each key shrinks from 1 + its length to 1 byte; decode becomes one integer jump per key instead of a string match; nothing changes for values and data.

Measured (task #2026, bench `crates/server/shamir-server/benches/wire_decode_measure.rs`): five builder-made requests, named encoding (`rmp_serde::to_vec_named`, the production form) against the positional "compact" form (`rmp_serde::to_vec`), which is a LOWER BOUND for the decode work of numeric keys (a numeric-keyed map still carries one key per field). Every scenario is executed once through the real handler on an in-memory database and its reply is checked BEFORE timing (`WIRE_DECODE_E2E_CHECK ok=true` for all five, in both runs). Two runs under `wnice -p idle -c 10 -t 8 -m 50` while other executors compiled on the same machine: the same cell differs by up to 2.9x between the runs, so read these as orders of magnitude. Times in microseconds, run 1 / run 2.

| Scenario | Request bytes named / compact | `decode_named` | `end_to_end` | Decode share of `end_to_end` |
|---|---|---|---|---|
| point read | 447 / 148 (3.0x) | 83 / 79 | 483 / 472 | 17% / 17% |
| single insert | 386 / 137 (2.8x) | 29 / 49 | 906 / 485 | 3% / 10% |
| batch of 1000 inserts | 73825 / 73576 (1.003x) | 48692 / 35386 | 1 iteration only: 30067 ms / 629 ms | not usable / 6% |
| nested filter and projection | 621 / 242 (2.6x) | 177 / 99 | 1875 / 1206 | 9% / 8% |
| DDL (create table, 3 indexes) | 756 / 507 (1.5x) | 91 / 165 | 701 / 776 | 13% / 21% |

Compact against named decode of the whole `queries` map (the largest part that round-trips in compact form): point read 78 -> 58 / 74 -> 28; nested filter 128 -> 109 / 185 -> 106; single insert, 1000-insert batch and DDL show no consistent gain (the differences are inside the noise, in both directions).

What the numbers support:

1. Bytes are the clear win: keyword overhead is 2.6-3.0x of the request for small reads, inserts and filtered reads, 1.5x for DDL, and nothing for data-heavy batches (1.003x).
2. CPU is a small win: decoding the whole request is 3-21% of the server-side time of a request (the handler, authorization and reply encoding are the other 79-97%), and the lower bound saves none to about half of that decode. A realistic ceiling for numeric keys is a few percent of request time (about 5% at best), before TLS and network time are added, which only dilute it further.
3. The full-request compact form does not even round-trip (`invalid type: boolean false, expected a string`: `BatchRequest.name` is `Option<String>` with `skip_serializing_if`, so every later position shifts). Positional encoding is therefore not an alternative; numeric-keyed maps (this design) are.
4. The 1000-insert end-to-end cell ran one iteration and varied by a factor of 48; its share is not a result. Run it with more iterations in step WIRE-DICT-5, on a quiet machine.

Owner decision of 2026-11-26: the dictionary is built in any case; the measurement supplies these numbers, it does not gate the work. Order of value: the encoder and the Rust client first (bytes), the TypeScript codec last (the most work, the same byte gain, no extra CPU benefit).

## 5. Risks

- A silent reorder of a wire type would mis-decode across versions: the snapshot test is the guard and runs in the fast tier.
- `skip_serializing`-only fields and `flatten` break index counting: rejected or marked `named` by the audit.
- Debugging: indexed frames are unreadable raw; the shell and a diagnostic decoder print them named through the dictionary.
- The TS type graph must follow every DTO change: the parity test catches drift.
