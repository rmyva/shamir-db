## Goal and why
1. A cursor that is closed (or reaches any terminal state) while a fetch of its next page runs must not be observable as live afterwards, and two terminal transitions must not both "win": today the terminal transition and the removal from the registry are separate steps, so a fetch can still read through a cursor that a close already ended, or a close can race a page. The rule is: the removal from the registry happens UNDER the cursor's state lock, the close sets an atomic terminal flag, and a fetch checks that flag AFTER it has taken the lock.
2. A refused read is a security-relevant event that leaves no trace today: `GetRecord`, the creation of a cursor and a cursor page can be refused (access denied, unknown or closed resource) without an audit record.

## Acceptance (three items)
1. **Atomic terminal transition (decided above).** Implement it in `cursor_handlers/fetch.rs` and the cursor registry (`cursor_registry/cursor/registry.rs`) so that: after a terminal transition no fetch returns a page from that cursor and the fetch reports the same typed outcome a closed cursor reports today; exactly one of two concurrent terminal transitions performs the cleanup; the session-cleanup path of a connection keeps its behaviour. Prove it with deterministic race oracles in the existing `tests/cursor/` layout (use the existing test seams and gates, never sleeps; absolute deadlines for every wait): a close that lands between the fetch's lookup and its lock acquisition, a close during a page, a double close. Each test states in a comment which broken implementation (flag checked before the lock, removal outside the lock, a second cleanup) it catches.
2. **Security audit event for refused reads.** For the refusals of `GetRecord`, of cursor creation and of a cursor page, emit ONE audit event of the Security class through the EXISTING audit queue (find how the other refusals are queued, including the bounded queue and its dropped-event counter): the event carries only names (database, repository, table, the operation) and the outcome, never record content, ids of other users' data or secrets. An unprivileged principal must not be able to inflate the log: coalesce repeats or apply a rate limit PER PRINCIPAL (choose, and state the rule and its constants in the report and in the guide; the event for a given principal is never silently lost in the sense of a different principal's flood). A successful read emits nothing. `repo_audit.rs` is at 980 lines and must not grow: the new logic lives in a NEW file with narrow members (members of new files that are `pub(crate)` or wider and not needed by a sibling are flagged by the CI rust-guard). The BATCH read path is NOT in scope (it waits for the name-to-descriptor window decision of task #2038): do not touch it and do not claim to cover it in the guide.
3. **Tests and guide.** Tests under the existing `tests/` layout: one per audited refusal (GetRecord, cursor creation, cursor page) asserting the typed event and its fields, the rate-limit/coalescing rule with a flood from one principal and an unaffected second principal, and a negative control (a successful read, and a refusal that is not a read, produce no such event).
