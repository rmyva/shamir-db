## Acceptance (three groups)

### A. The lock is released only when every step PROVED that its work ended

1. **P1: `release_clean()` is decided on the wrong evidence.** `shutdown_owner.rs:270-352` consumes the guard whenever the fallback-local `expired` is `None`; it ignores an outer timeout and earlier teardown errors, although the metadata-snapshot join says explicitly that its task may still own `server_meta` (`boot/runtime.rs:175-188`, `core.rs:733-754`), and a failed scheduler join clears the handle and then reports success to the quiescence check without proving that the native run ended (`shutdown_owner.rs:228-235`). DECIDED: the guard is consumed ONLY when the teardown ran to completion AND the report is clean (no error, no typed expiry) AND every settlement point returned PROOF; a join error, a cancelled join, an expiry of any bounded wait, a store-release probe that is not clean, and any "may still be running" outcome are NOT proof and leave the guard to leak. Express it once as a small typed value ("settled" or "unsettled with the stage") that every step returns, instead of `Option` flags spread over the function, and make the outer-timeout path and the fallback path use the same decision.
2. **P1: a failed boot can unlock over live work.** The guard exists only when `launch` returns a `ServerHandle` (`launch.rs:151-162,898-928`); both rollback arms can return after a cleanup timeout and drop the raw lock file while a detached task still owns a store (`support/rollback_cleanup.rs:63-81` detaches the metadata task on expiry). DECIDED: the lock is held by the same leak-on-drop guard from the moment it is taken until the end of the launch; a rollback that proves settlement releases it, a rollback that expired or could not prove settlement leaks it; the ORIGINAL boot error is returned unchanged in both cases. `launch.rs` must not grow: the logic lives in a new file.
3. **P1: producer quiescence is assumed, not proven, and the reaper bound is not end to end.** The shared helper proceeds after a connection survived its abort (`listeners.rs:388-426`, `launch.rs:777-808,845-855`) and `remove_all()` is not an admission fence (`tx_registry.rs:815-830`, `tx_abort_release.rs:68-81`); `release_source_stop.rs:49-68` times out, aborts, then awaits the same handle with no second bound (`shutdown_owner.rs:313-337` and `rollback_cleanup.rs:46-60` have no outer timer around it). DECIDED: bound the post-abort join with its own named bound taken from the existing budgets; when a producer or the reaper did not settle, the helper returns "unsettled" BEFORE it clears the registry or closes the tails, the caller records the typed stage and keeps the lock, and no log line claims that the sources were drained. A repeated call with no producers stays a safe no-op. A missed early return: `ticket_keys()`, `identity_state()` and `server_secrets()` can fail after the reaper was spawned and bypass both rollback arms (`launch.rs:544-584`, `http/boot_guard.rs:22-27`): resolve that fallible metadata BEFORE any reaper or listener starts, or route every post-spawn failure through the rollback rule of item 2.

### B. The binary leaves truthfully

4. **P1: an unwinding drain bypasses the bounded runtime shutdown.** Both entry points branch only after `block_on` returns (`main.rs:156-176`, `boot/policy/windows_service.rs:190-238`); a panic in the polled drain unwinds, ordinary runtime destruction can run during the unwind, and on Windows an escaping panic reaches the non-unwinding service callback. DECIDED: catch the unwind at both runtime-owner boundaries, take the same bounded runtime shutdown as the error path, and map the panic to exit code 70 (unclean) in the binary and to a defined non-zero service exit status in the service; nothing unwinds into the SCM callback. The lock is leaked by item 1 (an unwinding owner never consumes it).
5. **P1: a clean report can precede an unbounded runtime drop.** The HTTP listener logs login-worker and audit-consumer drain failures but can return success (`http/launcher.rs:434-467`, `http_login/service/audit.rs:234-244`): aborting the consumer does not stop an already running blocking append. DECIDED: those drain failures are surfaced as typed unsettled stages of the report (so the report is unclean, the exit code is 70, the lock stays); the cancelled SCRAM derivation that detaches a blocking job (`derive_scram_record.rs:64-93`) and the manual backup thread are NOT in scope: state each as a known limit in the guide (one sentence each, naming that a registry of background work is planned) and in your report; do not change the clean-exit policy.

### C. The typed report, the tests, the flake, the texts

6. **P2: the typed report is not enforced by the report.** `shutdown_report.rs:5-25,51-64,98-113` has a public setter that accepts arbitrary text, `is_clean()` ignores the stage, a second expiry overwrites the typed stage while both messages survive, and the reaper message can say "still running" after abort-and-join completed. DECIDED: the report API takes the typed stage (and the budget) and DERIVES the message; there is no setter that takes free text for an expiry; the report keeps the stages in order of occurrence and the singular accessor returns the FIRST one; `is_clean()` is false when any stage is recorded; the wording says that a wait EXPIRED, never that work is necessarily still running.
