## Findings to fix

### 1. P1: dropping the `shutdown()` future still releases the lock over live backup work
Round 1 declared this unfixable from inside and documented it. It is fixable and it is required: `ShutdownOwner` owns the lock file; cancelling the future before the final drain decision drops the owner and the file, which releases the lock over a live job (`core.rs` about 311-330, `boot/runtime.rs` about 106-161, `shutdown_owner.rs` about 164-183 and 317-325). DECIDED: the lock is released ONLY by an explicit, completed, clean drain. Any other end of the owner's life (a dropped or cancelled future, a panic that unwinds through it, an early return) leaks the file on purpose so the operating system keeps the lock until the process exits (the same mechanism you already use for an expired wait, expressed once, as a `Drop` guard around the lock file whose release is a consuming method called only at the end of a clean drain; a plain `Drop` leaks). The rustdoc then says what really happens instead of warning the caller. Replace the test at `owner_lock.rs` about 381-415, which awaits the spawned shutdown to completion and never cancels it, by a test that CANCELS the shutdown future while a scheduled backup job is parked (abort the task or drop the future at a deterministic point, driven by the existing probes and gates, no sleeps) and asserts that the lock is STILL held afterwards; and keep a test that a completed clean drain releases it. Also remove the ineffective deadline override you found: the wrapper passes `SHUTDOWN_DEADLINE` directly while `serve` uses `drain_deadline()`; make both read the same source.

### 2. P1: a bounded join does not bound the process exit of the binary
An expired wait ends as `Ok` with an abnormal report and exit code 70, and `crates/server/shamir-server/src/main.rs` (about 156-167 and 561-568) and `src/boot/policy/windows_service.rs` (about 226-231) use the bounded runtime shutdown only for the `Err` path. A blocking job already running (the backup reaches `flush_all_history`, `.../online_backup.rs` about 334, and the Fjall store awaits `spawn_blocking`, `storage_fjall/repo.rs` about 238-244) can therefore still hold the normal destruction of the tokio runtime indefinitely after the owner wait returned. DECIDED: when the shutdown report is abnormal (any expired wait, exit code 70) the binary leaves through the same bounded runtime shutdown as the error path, in `main.rs` and in the Windows service path, with the existing named bound (find it; do not invent a second one). The lock is leaked on that path by item 1, so the OS keeps it until the process is gone. Add a test at the level the code allows (the decision function that chooses the bounded path for an abnormal report, with the report values that occur) and say in the report which part cannot be tested without a real runtime hang.
