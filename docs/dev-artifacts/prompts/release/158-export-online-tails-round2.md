## Findings to fix (all P1 are mandatory)

### 1. P1: export-enabled servers falsely report their stores as still locked
`engine/server/server_handle/core.rs` (around lines 452, 714, 893) and `boot/config/diagnostics/logical/export_online/service.rs:239`: `take_shutdown_owner` clones the whole `OnlineExport`, which owns `Arc<ShamirDb>` and the durable user directory; stage 3b can establish the worker is idle and drop its own reference, but the fallback `ShutdownOwner` still holds those stores when stage 9 probes them, so an idle server with `export_root` configured can report `StillLocked` and exit 70 with no export running. Fix: `ShutdownOwner` keeps ONLY the worker-drain handle (a small type that owns no database or store reference), or the service reference is explicitly dropped after a successful stage 3b join, before the release probe. Add a regression test with an export-enabled server that is idle at shutdown: the release probe must report released (this is the production mistake the executor's own tests never exercised).

### 2. P1, CONFIRMED: `CancelTx` acknowledges cancellation before the locks are released
`engine/db_handler/repo_admin/activity/cancel.rs` lines ~300 and ~325-352. On `origin/master` `release_tx_locks` awaited the spawned release (`tokio::spawn(...).await`, logging a panic or a cancelled task) so the locks were gone before the reply; your branch calls `tails.spawn(work)` and returns, discarding the join, while the doc comment still says "awaited so that on the ordinary path the locks are gone before the cancel reply returns". The existing test `engine/db_handler/repo_admin/activity/tests/tx_release_tests.rs` lines ~491-504 asserts exactly that after the reply, so it fails in CI. Fix: the tracked spawn returns a completion receipt (or the join), the ordinary path awaits it, a dropped waiter leaves the task tracked and running; keep the failure logging for panic and cancellation. Keep the existing test unchanged and green by reading.

### 3. P1, CONFIRMED in the code, design to fix: release-tail close can lose cleanup or send it outside the owner
`engine/db_handler/repo_admin/activity/cancel.rs` ~333-350, `crates/server/shamir-sync/src/sync/durability/tx/tx_abort_release.rs` ~55-68, `engine/server/server_handle/core.rs` ~729, ~843-881 and ~892, `engine/server/server_handle/release_tail_drain.rs` ~31-40. (a) The handoff checks `is_closed()` and then `spawn()`: if close lands in between, `spawn` consumes the future, returns `false`, and the operator still reports `Cancelled` with the locks never released (the taken `TxContext` has no destructor that frees them); if close is seen first, the operator spawns an UNTRACKED tail. Make the handoff atomic and lossless (the registration under the same lock as the close latch, and on refusal the future is handed back or run inline under the caller's bound, never dropped, never detached). (b) Registry `Drop` after close discards the release; stage 3c observes zero with producers (the reaper, the last transaction reference) still open, and stage 8b closes even after a timed-out reaper join; in tests the handler can retain the registry until after 8b (`core.rs` ~892). Required order: stop and join the producers, explicitly empty the registry, THEN close and drain the release tails; the fallback owner joins the same producers. (c) The inline drains start a fresh 10 s clock and can be pre-empted by the outer timeout before they record their own error: use the stage deadline. Cover with deterministic tests where a seam exists (a late release registration after close is not lost; a refusal after close does not leak a lock).

### 4. P1: normal completion can cancel its own response
`engine/db_handler/repo_admin/execute.rs` ~500-539 and `engine/db_handler/handler/mutation_tracker.rs` ~38-41. After a successful `worker.await` the waiter does `drop(disconnect_cancel)` BEFORE `in_flight.finish()`; `DisconnectCancel::drop` always calls `try_cancel()`, and the engine does not necessarily leave the shared handle `Committing`/`Done`: an enrolled mutation rejected during authorization or planning returns while the state is still `Running` (`crates/engine/shamir-db/src/shamir_db/execute/repo_admin/db_execute.rs` ~96-100), and a successful batch whose conditional mutations all skip can take the same path. The guard then wins `Running -> Cancelled` and `finish()` replaces the real error with `cancelled`; the code comment "the state is already terminal" is wrong. Fix: an explicit `disarm()` on normal join completion (the guard fires only when the awaiting future is DROPPED mid-execution), and, if a disconnect must also be inert after the worker returned but before the waiter resumed, claim completion at the worker's completion boundary. Tests (current-thread or multi-thread, say which): an enrolled mutation refused during authorization answers its REAL typed error, not `cancelled` (positive control: dropping the waiter mid-execution does cancel the worker).

### 5. P1: cold-open admission is fenced only at handoff and the drain is skipped on lifecycle failure
`crates/engine/shamir-engine/src/repo/instance/repo_instance/lifecycle/recovery/clean_horizon_shutdown_impl.rs` ~24-58, `.../tx/commit/core/catalog_access.rs` ~94-109 and ~430-448, `crates/storage/shamir-storage/src/stores/storage_fjall/repo.rs` ~135-145. Fix: register the open BEFORE its first side effect and transfer the registration with the future; refuse fresh opens before they start with a typed error; close at shutdown ENTRY and attempt both drains under the shared deadline, preserving the original failure; correct the warning text.
