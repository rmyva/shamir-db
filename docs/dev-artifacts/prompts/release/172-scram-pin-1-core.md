## Goal and why
The owner decided to change the handshake before the first release so that the client verifies the server's pinned identity BEFORE it computes or sends any password-derived byte. The design (option A) puts a signature of the server's Ed25519 identity key over the challenge transcript into the challenge itself. This step builds the CORE pieces in `shamir-connect` and nothing else: types, the transcript and its sign/verify, the client-side verification rule including the rotation chain, the typed errors. It changes NO behaviour of the existing v1 flow: nothing here is connected to the wire yet (steps 2-4 do that), so master keeps talking v1 at every moment.
