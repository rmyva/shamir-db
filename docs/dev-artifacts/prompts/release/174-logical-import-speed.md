# Brief: LOGICAL-IMPORT-SPEED (task #2052, release blocker) - the offline logical import of a 1 GiB dump does not finish in 3000 s on any OS

You are session `li-1`, a NEW executor in a fresh worktree (`<worktree>`, branch `logical-import-speed`, created from the branch `dump-1gib-measure`, which already prints `LOGICAL_DUMP_PHASE` lines per phase from `crates/server/shamir-server/tests/admin/logical_dump/budget_tests.rs`). The offline `logical-import` is the portability path of release gate 4 (an export of one version is loaded by the next one); the design `docs/dev-artifacts/design/logical-dump.md` section 5 promised that a 1 GiB dump imports in at most 600 s.

## Facts (measured by CI, not guesses)
Dispatch run 45847870746 on the head of `dump-1gib-measure`, all three OS: the fixture of 112 649 records, 1 113 948 160 payload bytes, an artifact of 1 138 264 092 bytes and 2 tables was built in 241 / 495 / 700 s (ubuntu / macos / windows), exported in 54 / 172 / 178 s, verified in 10 / 16 / 25 s, and the IMPORT hit its 3000 s cap on every OS (`Elapsed`, `budget_tests.rs:301`; whole test 3313 / 3700 / 3927 s). The 64 MiB variant of the same run finished in 139 s on ubuntu, so the cost per record is about the same at both sizes (17-26 ms per record): the growth is linear in the number of records and the import is about 55 times slower than the export. Hypothesis to confirm or refute by reading and by measurement, not to accept: `load/stage_load.rs::load_record` writes every record with its own `table.set(RecordId(key), &inner)` into a freshly initialised staging engine (`ShamirDb::init`, default durability policy), so the cost is one synchronous commit per record; the file header says "bounded batches" but the code does one record at a time; it also asks the repository interner for its handle on every record and persists it every 500 records.
