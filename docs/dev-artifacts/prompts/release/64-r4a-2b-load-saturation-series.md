## Why

An operator needs to see saturation BEFORE clients see refusals: how close the server is to its connection cap, how many connections were turned away, whether the response byte budget or the password-hashing pool is the thing everything waits on. Two series of the old design list cannot be delivered honestly (a per-database session count: a session is not bound to a database; an admission queue depth: there is no queue, admission is a cap plus bounded waits). This step replaces them with the series the code can really support and records the decision.

## What (this step only)

1. **Decide the set from the code, then implement it.** Read the sources above and confirm each candidate has a real, cheap source; implement only those that do, and list the rest with the reason in the report. Expected set (adjust to what the code supports; names stay in the reserved `shamir_` space, no per-user/per-session/per-IP labels, only a bounded `transport`-style label if the code has several accept loops with separate caps): `shamir_connections_active` (gauge) and `shamir_connections_limit` (gauge, 0 = unlimited) from `ConnLimiter`; `shamir_connections_rejected_total` (counter, a new atomic at the `try_acquire == None` site — one relaxed `fetch_add` on an already-cold refusal path); `shamir_response_bytes_in_flight` and `shamir_response_bytes_budget` (gauges) and `shamir_response_budget_waiters` (gauge, only if a waiter count can be kept without a lock and without a cost on the uncontended path) from `ByteBudget`; `shamir_argon2_in_flight` and `shamir_argon2_waiters`/`shamir_argon2_capacity` (gauges) from the Argon2 semaphore; rate-limit refusals (per-session bucket, auth-init limiter) as counters ONLY if they are not already represented by the existing token/auth counters (no duplicate series: check `auth_attempts_total{result}` and the token counters first). NOT delivered, with the reasons recorded in the guide and the report: a per-database session series and an admission-queue-depth series.
2. **Sources and cost.** The servers own the atomics (lock-free; no `Mutex`/`RwLock`; no `len()` on `scc` maps; `Relaxed` counters where only monotonic totals are read; read the memory-ordering notes of the existing gauges); the export module samples them at scrape time through a small trait/handle bound at boot (the pattern of the activity gauges), so the hot path gains at most one atomic add on a REFUSAL path and nothing on the success path. Layer rule: metrics flow downward only; a lower crate never references the server-security export. If a source lives in a crate the export cannot see, pass a handle down at boot (as R4b step 1 did) — list every new edge and every changed signature.
3. **Export tests (CI-only).** For each series: a sampled value test against the real source (open N connections against a limiter with a small cap, assert `active`, `limit`, one `rejected_total` increment per refused acquire and no increment on success; budget in-flight equals the reserved bytes and returns to 0 after the guard drops; Argon2 in-flight rises while the permits are held and returns to 0), a launcher-level scrape test through the real `/metrics` route that the series are present with the right values for THIS boot (the pattern of `activity_gauge_binding_tests.rs`), and a "no label leak" test that no series carries a user name, address or session handle. Use persistent stores, handshakes not sleeps, bounded awaits (at least 120 s), `argon2_concurrent_max` and `auth_init_rate_per_second` 64 in multi-session fixtures.
4. **Guide (Russian, `docs/guide-docs/guide/07-operations.md` §3 `/metrics`).** Add one row per delivered series (type, labels, meaning, normal range and what a deviation means) next to the query-metrics rows; REPLACE the paragraph that says the load series are not added with an accurate one (what was added, what is deliberately absent and why: no per-database session count, no admission queue — the cap/semaphore/budget series above are the saturation signals). Every statement must match the code.
5. **Design note.** Update `docs/dev-artifacts/design/engine-metrics.md` §2 Load rows to the delivered reality in the same change (two short lines: delivered names; the two series dropped and why), keeping the document's own conventions.
6. **CI selection:** check `scripts/ci/matrix/` selects the changed crates' tests on the three OS; widen only where a target is not selected, and list it.

## Do not

Add a series without a real source, per-user/per-IP/per-session labels, a lock or an allocation on the success path of accept/admission/response, a dependency, change any limit's behaviour or default, touch the activity gauges' names or semantics, add the dashboard or alert rules (task R4a-6 owns them), touch the TypeScript clients, weaken an assertion, use sleeps for synchronization, or widen an existing item beyond what the new code needs (list every widening).

## Layout and fixture lessons

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`. Persistent stores, every `TempDir` alive for the whole test, close handles and wait for the server task to finish before reopening a directory (Windows holds Fjall locks until the dropped engine's background handles finish: reopen with a bounded retry on `Locked` only, like `init_waiting_for_locks` in the function-family crash tests), handshakes not sleeps, every await bounded by a generous timeout (at least 120 s: a hang detector, the Windows runner is up to 10x slower), a batch is at most 50 queries, per-session request rate limit 500 req/s (never poll in a tight loop: pace status polls at 20 ms or more), set `argon2_concurrent_max` and `auth_init_rate_per_second` to 64 in fixtures that open several sessions, debug-test stacks are small (call concrete handlers through `Box::pin`, run deep tests on a roomy thread, `on_big_stack`), assert on invariants and sets, `shamir-test-diag` marks for flake-prone tests.

## Rules that bind the change

* Machine memory: at most ONE cargo command at a time machine-wide (other executors run: if a cargo run is already in progress wait for its notification, never poll), ALWAYS as `bash /d/system_artefact/orch/cg.sh env RUSTC_WRAPPER= wnice -p idle -c 50 -t 8 -m 50 -- cargo ... -j 1 > <logfile OUTSIDE the repository> 2>&1` (the wrapper serializes cargo across executors; never `-j 2`; never piped through `tail`/`head`; `cargo fmt` rejects `-j`: run it with `CARGO_BUILD_JOBS=1` under the same wrapper); every worker you spawn must be told the same, and no worker may run cargo at all except `check`/`clippy`/`fmt` under these rules.

* Wrap-up: by 150 minutes bring the change to a compiling, formatted, clippy-clean state and stop; say in the final report what is missing.
