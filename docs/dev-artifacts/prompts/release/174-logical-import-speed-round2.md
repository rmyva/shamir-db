## Acceptance (three items)

1. **P0: the batches must be bounded by bytes, not only by record count.** The 1 GiB fixture has 640 large records of 256 KiB (`budget_tests.rs:356-364`, `fixture.rs:73-78`), the export visits `bulk/large` before `bulk/many` (`logical_dump/driver.rs:343,710-739`), so the first batch of 512 records carries 128 MiB of blob bodies in ONE transaction; the pipeline encodes one WAL frame per transaction (`locked.rs:173-197`, `repo_wal_manager.rs:115-126`) and a frame over 64 MiB is rejected (`wal_segment.rs:307-311`, `frame_reader.rs:9-12`), so the 1 GiB import fails at its first batch. A batch of 512 x 10 KiB (about 5 MiB) is fine. Close a batch when EITHER the record count OR the encoded bytes reach their cap, FLUSHING BEFORE the next row would exceed the byte cap (leave room for the encoded WAL overhead; take the limit from the code, not from this text); add a test at the boundary (a single row near the cap, a row that would cross it, a count-bound batch, a byte-bound batch). Also add the cancellation-token check before every full or tail commit (a cancelled import must not issue another commit; the CLI joins on cancellation and a dropped future can detach a commit and leave a stage: say in the report what is left behind and that the retry path cleans it).
2. **P1: the per-row upsert pre-read keeps the load quadratic on Fjall, and it may be the REAL dominating cost of the original 26 ms per record.** `tx_update.rs:35-40` reads the old row; a new id misses the staging overlay and takes the snapshot history fallback (`table_manager_streaming.rs:660-674,723-736`, `mvcc_store/store.rs:449-455`, `mvcc_history.rs:27-48`); the wrapped store delegates to Fjall's FORWARD `iter_range_stream`, which starts at the beginning and filters instead of seeking (`storage_membuffer/store_impl.rs:229-261`, `shamir-storage/src/core/types.rs:478-503`), so with ascending keys each miss walks the already drained prefix. The old `set` did the same cold history seek (`version_entry.rs:346-389`). The measured numbers fit a small linear base plus an O(n) walk: 17.6 ms per record at 64 MiB (6.8 thousand records) and at least 26.6 ms per record at 1 GiB (112 649 records). Remove this cost for the fresh staging store: either a native bounded seek for the history lookup (if it is a defect of the storage layer for every caller, say so) or a narrowly scoped insert path that does no pre-read on the fresh stage, where duplicate ids are already refused before the load (`stream/state.rs:124-132,271-275`, `stage/dir.rs:105-135`). Decide with the code in front of you, state the complexity of the OLD and the NEW path with the cited lines, and keep every guarantee of the published database (durability barrier before publication, validation, the exact 16-byte ids, the interner persistence cadence). If you touch a crate outside `shamir-server` (`shamir-storage`, `shamir-engine-table`, `shamir-tx`), keep the change minimal and name every file; `crates/engine/shamir-engine/**` and the engine tx layer belong to another executor and stay untouched.
3. **The tests and the diagnostics must be able to fail for the right reason.** (a) The published read-back test opens the home but never opens `bulk/many` and `bulk/large`; the facade refuses unopened tables and WAL replay may open them by accident (`import_durability_tests.rs:78-95`, `logical_export/reader.rs:206-209,349-358`, `recovery/v2.rs:105-125`): open both tables explicitly before the freeze, as production validation does (`load/validate.rs:39-50,147-164`), and either add a flush-specific negative control or narrow the test's claim (WAL replay can recover rows without the final flush, `recovery/v2.rs:431-448,553-563`). (b) The commit counter is a writable global shared by every import in the `admin` test binary: replace it by an attempt-local count that the import reports (no `pub static`, no new public re-export), and assert the EXPECTED count for the fixture and the byte/count policy, not a range that accepts mostly per-row commits (`import_durability_tests.rs:172-198`). (c) Split `record_load` into sub-timers (decode and conversion, staging, commit, periodic interner persistence) and time the stages the lines omit today (preflight, close waits, receipt hashing); print a `record_load` line also when loading fails or is cancelled (`driver.rs:62-70,148-159,185-221`, `stage_load.rs:125-127`).
