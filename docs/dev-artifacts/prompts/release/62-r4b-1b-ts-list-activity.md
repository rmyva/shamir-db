# Brief: R4b step 1b — TypeScript client for the activity view: typed `ListActivity` request builder, `ActivityPage`/`ActivityRow` types with exact u64 handling, `ShamirClient.listActivity`, tests, guide note

Design (settled and LANDED): `docs/dev-artifacts/design/operational-views.md` §5.1 (wire ops and DTOs), §5.2 (permission: `scope: Own` any authenticated user, `scope: All` needs `ActivityView` + Manage; the op is a SCRAM-session surface only, API-token requests are denied with `token_request_denied`), §5.3 (client methods). This task is the TypeScript mirror of the Rust half that has LANDED (R4b step 1): read it and mirror its SEMANTICS, not its structure — the wire DTOs `crates/query/shamir-query-types/src/admin/activity/` (`list_activity_req.rs` with the hand-written flat-tag serde: the presence-only `list_activity: true` discriminator sits flat next to `scope`, `kind`, optional `limit`, optional `continuation`; `activity_row.rs` tagged by `kind`: `session` / `request` / `transaction` / `cursor`, with `ActivityRequestState` `running|done`, `ActivityTxState` `active|awaiting_commit|expired_pending_reap`, `RequestExecId` transparent u64, `Request.session_handle` OPTIONAL and omitted on the wire when absent; `activity_page.rs`), the Rust builder `crates/query/shamir-query-builder/src/wire/admin/list_activity.rs`, the Rust client method `list_activity` in `crates/client/shamir-client/src/client/api.rs` (it drives the raw round trip and expects the TOP-LEVEL `DbResponse::ActivityPage { page }`, NOT a `Batch`), the server handler `crates/server/shamir-server/src/engine/db_handler/repo_admin/activity/` and the wire enum `crates/query/shamir-query-types/src/wire/db_message.rs`. Re-open every path before relying on it. The migration tool of R1c-3b (`src/core/builders/admin/schema-migration/`: `wire.ts`, `client/client.ts`, `client/decode.ts`, `client/error.ts`) is the pattern in THIS package for typed wire builders, strict u64-safe decoding and a tool composed over `ShamirClient` instead of growing `client.ts`.

## Why

Release gate: "an operator can find and cancel a stuck query". The Rust client and the server already list activity; TypeScript applications and tooling need the same typed, builder-only, privacy-safe call (no hand-built wire objects), with correct u64 handling (session handles, execution ids and nanosecond timestamps exceed 2^53).

## What (this step only)

1. **Types.** `ListActivityRequest` (`scope: 'all' | 'own'`, `kind: 'sessions' | 'requests' | 'transactions' | 'cursors' | 'all'`, optional `limit` u32, optional `continuation` string), `ActivityRow` as a discriminated union on `kind` mirroring the four Rust variants field-for-field (camelCase in TypeScript only if the package's convention maps wire snake_case to camelCase for decoded results — read how existing typed results (for example the migration status result, token admin results) name fields and follow it exactly; the WIRE names are the Rust serde names), `ActivityPage { rows, continuation? }`. u64 fields (`session_handle`, `request_exec_id`, `tx_handle`, `cursor_id`, `pinned_version`, `created_at_ns`, `idle_ns`, `elapsed_ns`, `open_ns`) are validated as safe non-negative integers and normalized to `bigint` exactly like `schema-migration/client/decode.ts` does (`number | bigint` in, `bigint` out, range-checked to u64), counts that are Rust `usize` (`open_transactions`, `open_cursors`) are plain non-negative integers. Strict decode: unknown row `kind`, a missing or mistyped field, an unknown state string → a typed decode error (never guessed, never a partially filled row).
2. **Builder.** `listActivity(request)` producing EXACTLY the serde wire shape of `ListActivityReq` (flat tag `list_activity: true`, no marker field in the typed surface, absent optional fields omitted, never `null`), validated on build (limit in u32 range, known scope/kind) with the package's usual typed error. It is one more member of the TS batch-op union: list that widening. Follow how the other admin ops are exposed from `src/core/builders/admin/` and how `Batch` accepts them (no raw wire objects anywhere in new code or docs).
3. **Client method.** `ShamirClient.listActivity(db, request)` (or a small composed tool object if growing `client.ts` (803 lines) is unwise — decide, say why) sends the op as the sole entry of a standalone batch and accepts ONLY the top-level response kind `activity_page`; an `error` response goes through the package's existing error mapping (so a denied `scope: all`, an old server that does not know the op, and the token-denial case surface as the typed `ShamirDbError` with the server's code), any other response kind is a typed protocol error. Read `execute` in `src/core/client/client.ts` (it unwraps only `kind === 'batch'`) and the raw round-trip helper next to it: add the narrowest raw path; do not change `execute` behaviour. A continuation walker helper (`listAllActivity`/async iterator, bounded by the caller's page limit, stops when `continuation` is absent, never loops on an empty continuation) is allowed ONLY if it is a thin function over `listActivity`; a safety cap on pages is required.
4. **No privacy regression.** The decoded page must not carry anything the server did not send; the client never logs rows; add no field that could hold a token.
5. **Tests (vitest, deterministic; read `src/core/client/__tests__/` and `src/__tests__/e2e-harness.ts` first).** Builder wire-shape tests (exact map, optional fields omitted, flat tag, validation refusals); decode tests (every row variant, optional `session_handle` absent, u64 above 2^53 as `bigint`, every strict refusal); a scripted-transport test that `listActivity` sends exactly one request and unwraps `activity_page`, that an `error` response maps to the typed error, that a `batch` response is a protocol error; the walker's page cap; and ONE real-server e2e in `src/__tests__/` (`describe.skipIf(!SERVER_AVAILABLE)` like its siblings): an admin session lists `scope: 'own'`/`kind: 'sessions'` and sees its own session, a second ordinary session sees only own rows and is DENIED `scope: 'all'` with the typed code, pagination with `limit: 1` walks to exhaustion. Cross-check the wire map against a vector produced by the Rust builder if a shared fixture pattern exists (the migration vectors are the precedent); if you add a fixture file put it next to the Rust builder tests and read it by relative path from the TS test, never copy it, and check `scripts/ci/matrix/edges.toml` so a change to it selects the TS tests (list the edge as a widening).
6. **Guide.** A short section in the TS client docs (`crates/client/shamir-client-ts/docs/`, confirm the existing file names first; extend an existing guide or README section, do not invent a docs tree): listing sessions and requests, scopes and permissions, the SCRAM-only note (API tokens are denied), paging, u64 as `bigint`, what rows never contain. Builder-only examples.
