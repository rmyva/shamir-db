# Brief: remove `chrono` from the workspace (advisory RUSTSEC-2026-0543: unmaintained) — the `datetime/` scalar functions and the record-id epoch go to `jiff`/`std` with a differential parity proof, the deny exception is deleted

Context: `deny.toml` carries an ignore entry for RUSTSEC-2026-0543 with the reason "migration to time/jiff changes datetime function semantics and is a separate, deferred, parity-tested project". This is that project. In `Cargo.lock` only two workspace crates depend on `chrono`: `shamir-types` (`crates/foundation/shamir-types/src/types/ids/record_id.rs`: `use chrono::Utc`, a wall-clock epoch read and a doc comment naming a `chrono` constant) and `shamir-funclib` (`crates/query/shamir-funclib/src/functions/datetime/core.rs`, 379 lines: `StrftimeItems`/`Item::Error` pattern validation, `DateTime<Utc>`, `NaiveDate(Time)`, `Duration`, `Weekday`, `Timelike`/`Datelike`, RFC 3339 parse and format; tests in `datetime/tests/datetime_tests.rs` use `chrono::{DateTime, TimeZone, Utc}`); `crates/engine/shamir-engine-validator/src/validator/schema/rules/format.rs` only MENTIONS `chrono::DateTime::parse_from_rfc3339` in a comment (the `date-time` format rule is a regex: leave the regex alone, fix the comment). `jiff` 0.2.x and `time` 0.3.x are already in `Cargo.lock` as transitive packages (re-read `Cargo.lock` and `cooldown.toml`/`cooldown-exceptions.toml`: a package version already present in the base lock needs no admission; a NEW version would). Dependency admission rules: `scripts/ci/gates/dependency_admission_check.py`.

## Why

An unmaintained date/time crate sits under user-visible functions. The advisory exception must go, not be renewed, and user-visible behaviour must not change by accident.

## What (this step only)

1. **Behaviour inventory first (in the final report).** From `core.rs` and its tests, list for every function of the `datetime/` family (`now to_epoch_s to_epoch_ms from_epoch_s from_epoch_ms parse_rfc3339 format_rfc3339 parse format year month day hour minute second weekday is_weekend add_secs add_days diff_secs start_of_day start_of_week start_of_month truncate age`) the exact observable contract: accepted input forms, output form, rounding/truncation (milliseconds, fractional seconds in RFC 3339 output, sign and range of years), `weekday` numbering and `start_of_week` convention, the strftime specifiers the pattern functions accept and the ones chrono rejects (the machine code `"parse"` for an invalid specifier, a non-matching input, an unparseable string), `"out_of_range"` boundaries (the exact `i64` millisecond limits chrono accepts), `"bad_unit"`, the checked-arithmetic cases. State what `jiff` (and `std` for the record id) does differently for each. Decision rule, binding: **preserve every behaviour that is documented in the module doc, the function registry docs or the existing tests**; where `jiff` differs, implement the chrono-compatible behaviour with explicit code (range checks, specifier whitelist, formatting by hand) rather than inheriting the new behaviour. A behaviour you believe cannot be preserved is listed in the report with evidence and the alternative; do not change it silently.
2. **Differential parity proof (CI is the oracle; nothing runs here).** Phase A (the change as pushed for the first CI run): the new implementation lives in the production path, and `chrono` stays ONLY as a `[dev-dependencies]` entry of `shamir-funclib` with a differential test that runs the OLD logic (copied verbatim into the test module as the reference oracle, clearly marked and self-contained) against the new functions over a generated input set: a dense grid around every boundary (the `i64` ms limits, year 0/1/9999/negative years, leap days and leap years incl. 1900/2000/2100, month and year ends, DST-free UTC only, sub-second values, negative epochs), every `truncate` unit including the unknown one, a table of valid and invalid strftime patterns (every specifier chrono knows plus junk), RFC 3339 strings (with/without fraction, offsets `Z`/`+hh:mm`/`-hh:mm`, lowercase `t`/`z`, leap second `:60`, malformed), and a deterministic pseudo-random sweep (a fixed seed, no `rand` dependency: a small xorshift in the test). Equality of the full `Result` (value or machine code). Phase B (a second change in the same branch, done by you only after reading the result is plausible, but the orchestrator will run CI on Phase A first and tell you the outcome in a follow-up if anything diverges): delete the oracle and `chrono` from `shamir-funclib`'s manifest, keep golden-vector tests with literal expected values for the contract of item 1. Because you cannot run anything, deliver Phase A as the state of the tree and ALSO prepare Phase B as a documented patch description in the report (exact files and lines to delete and the literal golden vectors you derived by reasoning, flagged "derive-from-oracle-in-CI" where you are not certain): the orchestrator performs Phase B after the differential run is green. The final removal of `chrono` from every manifest and the deny entry happens in Phase B.
3. **Record id.** Replace the `chrono::Utc` use in `record_id.rs` with `std::time::SystemTime` (epoch microseconds; keep the exact value semantics and the constant `EPOCH_2026` or whatever it is called; a pre-1970 clock is handled as today) and fix the doc comment that names the `chrono` call to a literal or a `std` description. A unit test pins the constant to its literal value (computed arithmetically, e.g. days-from-civil by hand, not by a date library).
4. **Comment fix** in `format.rs` (mention of `chrono::DateTime::parse_from_rfc3339`: describe the RFC 3339 grammar the regex accepts without naming the crate).
5. **Manifests and policy (Phase B list in the report, Phase A state in the tree).** `shamir-types`: remove `chrono`. `shamir-funclib`: add `jiff` (version already in the lock, minimal features: only what the functions need; check whether `std`/`alloc` and the bundled tz database features are default and turn off what UTC-only functions do not need) and keep `chrono` as a dev-dependency in Phase A only. `deny.toml`: delete the RUSTSEC-2026-0543 ignore (Phase B, with the comment block). `Cargo.lock` is regenerated by the orchestrator (say which lock entries must disappear: the `chrono` package and its exclusive transitive dependencies). The CLAUDE.md note about dependencies: state the trade-off of adding `jiff` as a direct dependency (size, compile time, already in the lock) in the report. If after the change another package still pulls `chrono`, list which and keep the exception.
6. **Docs.** The function reference of the datetime family (search `docs/` for the documented contract of these functions) changes only if a documented behaviour changed (it must not); add one line to the release notes/changelog file if the repository has one for such changes (check `ls`; do not invent one).

## Do not

Change the canonical timestamp type, the function names, their arity or purity flags, the machine error codes, or the `date-time` regex; add `time` AND `jiff` (choose one: `jiff`, because the functions need strftime-style patterns); add a registry package that is not already in the lock; weaken an assertion; use a build or test run to "check"; keep `chrono` in any manifest after Phase B; widen an existing item beyond what the new code needs (list every widening).

Count every folder you add to with `ls` (many are at 7 entries: `python -I scripts/ci/check_layout.py` counts only tracked files, recheck after staging); at most 1000 lines per file, one primary item per file, `mod.rs` re-exports only (the rust-guard structure gate allows nothing else in a `mod.rs`: shared helpers go in a named file), tests in `tests/` folders, no inline `#[cfg(test)]` modules, no local `use`, no new `#[allow]`.
