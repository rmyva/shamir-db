## Findings to fix (in this order)

### 1. The export sequence cannot work across batch invocations (P1, design decision made by the orchestrator)
Facts (verified): every batch invocation opens its own session (`shell/parser/run.rs`, `run_batch`); the server job is OWNED by the session that started it and is cancelled when that connection closes; status and cancel resolve the job by the session handle and the database of the request envelope, there is no job id. So a batch `start` that returns after the receipt cancels its own job, and a second process can neither see nor cancel it. The guide sequence of separate processes is wrong and the lifecycle, cancel and golden tests repeat it.
Decision (do not re-open it, do not touch the server):
- Interactive mode: `export online start` returns after the receipt; `export online status` and `export online cancel` work in the SAME interactive session.
- Batch mode: `export online start` HOLDS its session until the job is terminal (poll `ExportStatus` on the same session at a fixed interval of one second; a bounded total wait taken from the existing global timeout option if the shell has one, else a documented fixed upper bound), then emits ONE JSON Lines v1 record with the terminal status (success with the opaque artifact label, or the typed failure/cancelled outcome). Killing the process closes the connection and the server cancels the job: say so in the guide. Batch `export online status` and `export online cancel` are refused BEFORE any request with a typed usage-class refusal whose stable reason says that a job belongs to the session that started it (no wire operation is sent; the op field stays null). Reuse the existing refusal machinery and exit codes; do not invent new exit codes.
- The `start` request must put the REQUESTED database into the request envelope (the server rejects a mismatch with the envelope database: `src/engine/db_handler/repo_admin/support/export_gate.rs` around lines 166-173). Same for status and cancel.
Rewrite the guide chapter, the help text and the tests to this behaviour. The guide must not promise a job id, a retrieval path or cross-process control.
