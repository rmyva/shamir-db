## Items

1. **Control files are read through static links (P1, v1 verify and restore).** `manifest.json` (`offline.rs` `verify_manifest_impl`, `restore.rs` manifest read) and `format.stamp` (`format_stamp/io/inspect.rs`; restore reads it even when a v1 manifest does not list it) are read with an ordinary open that follows a symbolic link: a link named `manifest.json` gives the verdict `verified` from an EXTERNAL manifest, a link named `format.stamp` that the manifest does not list gives the format epoch for restore. Required: a control file must be a plain non-link regular file and is read through the same no-follow open the other snapshot files use; an absent stamp stays acceptable, a link does not. The attacker model is a writer into the snapshot directory (so this is "the same hole" class, not a new escalation); say so in the code comment and in the guide wording if the guide states the guarantee. Cover both verify and restore, both control files, on every platform the checks run on (a Windows reparse point is a link too), each with a positive control (a plain file passes) so a missing file cannot fake a refusal.
2. **Check-then-open is not bound to one object (P2, also in v2).** The path check and the later hash or copy are not bound to the same object (`offline.rs` around the `DirEntry::file_type` checks and the hash/copy; `restore.rs` around the copy; `restore/staged_listing.rs` checks only presence and type, not the copied bytes). Required: anchor the source directory, open each file no-follow once, take type and size from the opened handle, hash the bytes that are actually copied, and publish only after that hash matches. If a fully race-free design needs a platform primitive the code base does not have, implement the strongest bound that the existing helpers allow (open once, verify on the handle, hash the copied bytes before publication) and document the residual window precisely as a known limit.
3. **The `schedule` section of the BackupStatus reply comes from a process-level cell (production, found by the REL-R2d-P5 review).** Two servers in one process (embedding, tests) see each other's schedule state: a server without a schedule reports its neighbour's, and stopping one erases the other's section. Required: the cell lives inside `OnlineBackupRegistry`, shared by its adapter and its scheduler, with generations used only for replacement inside that registry; a test with two distinct registries (one scheduled, one not; stopping one leaves the other's section intact). In production there is one server per process, so this is correctness for embedding and tests.
4. **Scheduled-backup test strength (P5 tests).** (a) no test drives a real scheduled SUCCESS with a window and a controlled clock (assert `done`, no `reason`, the real next due time, and that a stale generation's next-run write is rejected); (b) no test publishes BEFORE and AFTER retention (park the runner before the final publication; the scheduled run exposes a `finished` signal); (c) no deterministic abort before and after the first poll; (d) the failure test exercises preflight, not a copy failure; (e) the warning "scheduled backup run failed" is now emitted INSIDE the registry write lock and under target `metrics` (it was outside the lock, target `registry`): decide, from the code, whether the lock scope is a defect (emit after releasing the lock) and fix or justify; (f) `next_run_unix_ns` saturates at u64 for an interval over 500 years: keep u128 until the adapter; (g) the comment about generation wrapping is inaccurate: correct it.
