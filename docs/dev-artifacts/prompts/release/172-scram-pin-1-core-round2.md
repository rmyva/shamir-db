Rewrite the decode as a validator over the raw bytes that reads the MessagePack markers itself (no serde in the decision): the root is an array marker (`fixarray` or `array16`/`array32`) of exactly 3 elements; elements 0 and 2 are `bin8/bin16/bin32` of the exact value lengths 32 and 64 (any valid wider `bin` marker for the same value is ACCEPTED); element 1 is an unsigned integer marker (`positive fixint`, `uint8/16/32/64`; a signed marker `int8..int64` or a negative fixint is refused even when the value is non-negative) and stays a lossless `u64`; the whole input is consumed exactly once (a byte after the triple is refused). EVERY violation returns `Error::ChallengeLayout`, and nothing panics on any input (bounded reads, checked lengths, no indexing without a length check, no allocation sized by an attacker-controlled length before it is checked against the remaining input). Keep `ChallengeRotationPayload` and its callers unchanged. Add the shared accept/reject byte vectors of rule 8 for the INNER triple as `crates/net/shamir-connect/test-vectors/challenge_layout_v2.{json,toml}` (same style and two formats as `challenge_identity_v2.*`; every row is a hex string written BY HAND from raw marker bytes, never produced by `rmp_serde`, so that they pin the layout independently of the encoder; one row per case, a name and the expected outcome per row): ACCEPT = the canonical `bin8` form, `bin16` and `bin32` markers for the same two values, the deadline under `positive fixint`, `uint8`, `uint16`, `uint32` and `uint64` markers for values that fit and `uint64::MAX`; REJECT = root is a map; arrays of 2 and of 4 elements; an array of 32 integers instead of `bin`; a `str` marker instead of `bin`; `bin` of 31, 33, 63, 65 bytes; a signed `int8`/`int64` marker and a negative fixint for the deadline; a float marker; one byte after the triple; a truncated input at every element boundary; an empty input.
