# Brief: R1c step 3a — migration tool in the Rust client `shamir-client` (status / plan / apply, no blind retry) and the shared canonical vector file

Landed and available: the typed model and canonical form in `crates/query/shamir-query-types/src/admin/types/schema_migration/` (`model/`, `canonical/`, `protocol/` DTOs: `SchemaMigrationStatusRequest/Result`, `SchemaMigrationPlanRequest/Result`, `SchemaMigrationApplyRequest/Result`, predecessor, submission), the Rust builders in `crates/query/shamir-query-builder/src/wire/schema_migration/` (`SchemaMigration` body builder, `SchemaMigrationSet` with `canonical_bytes()` and `checksums()`, `application_schema_status/plan` and `apply_application_schema_migration` batch ops) with their golden tests, and the server handlers (status, plan, apply with resume, function/validator operations) in `shamir-db`. Read the protocol DTOs and the server handlers' result shapes (`status`: applied prefix, last applied id, in-flight record with status, in-doubt reason, pending operation index, fence generation; `plan`; `apply`) before designing the client types. This task is the Rust half of `#1928`; the TypeScript half starts after this one lands and consumes the vector file this step creates.

## Why

Applications ship their schema changes as an ordered, checksummed migration set. The client tool is how an application applies the next change safely against a server that journals, fences and reconciles. It must make the safe path the easy path: compare the local set with the server journal before anything is sent, send exactly one next ordinal, and after any uncertain outcome ask the server what happened instead of resending.

## What (this step only)

1. **Migration set in the client.** A client-facing type that wraps the existing `SchemaMigrationSet` (do not re-implement bodies, canonical bytes or checksums): ordered by ordinal, contiguous from 1, unique ids; construction validates and returns a typed error. No filesystem discovery, no raw wire values: the set is built from the typed builders only.
2. **Operations on `ShamirClient`** (home named after counting entries, see Layout): `status`, `plan`, `apply_next`, each sending the typed admin batch operation of the builders through the existing `execute` path (interner/epoch handling stays untouched):
   * `status(db, target identity)` → a client result that compares the server journal with the local set: applied prefix, the next local ordinal to apply, DRIFT (an applied ordinal whose recorded id/checksum differs from the local body), GAP, local set shorter than the journal, in-flight owner/status, in-doubt operation index and reason. Pure read.
   * `plan(...)` → the server's plan for the next ordinal (exact next migration, checksum checks, warnings, dependency edges, function-code preflight outcome); never writes.
   * `apply_next(...)` → refuses BEFORE any send when the local set shows drift, a gap, a checksum change of an applied body or nothing left to apply (typed errors); otherwise submits exactly one next ordinal with the expected predecessor and the fence generation the status reported, and returns the server's result.
3. **No blind retry (§5.3).** A transport error or timeout after an apply was sent returns a dedicated typed error carrying "outcome unknown; query status" and does NOT resend. A helper `resolve_unknown_apply` (or equivalent) runs `status` for the same migration id and maps the outcome: applied with the same ordinal and checksum → success; in-flight / in-doubt → the typed in-doubt error with the server's reason; not applied → tells the caller it is safe to call `apply_next` again. The identical-body resume path of the server is reachable through `apply_next` again; document it.
4. **Typed errors.** Map the stable server codes of §5.3 (`schema_migration_in_progress`, `_in_doubt`, `_checksum_mismatch`, `_gap`, `_predecessor_mismatch`, `_follower_read_only`, `_durability_unavailable`, `_postcondition_failed`, `_identity_mismatch`) and the `schema_migration_operation_deferred:` refusal prefix into one client error enum without losing the server message; an unknown typed operation from an old server becomes a distinct unsupported-server error. No code path falls back to individual DDL calls.
5. **Shared canonical vector file.** Create the single source of truth for cross-client vectors, committed under the query-builder crate (name the path; a JSON file with: migration id, ordinal, name, a language-neutral description of each operation, the expected canonical bytes in hex and the expected SHA-256 checksum in hex) covering EVERY one of the 19 operation kinds plus function dependencies, ordering and `if_not_exists`-style optional fields; add a Rust test in the query-builder crate that rebuilds each case from the typed builders and asserts bytes and checksum equal the file (the TypeScript step reads the same file). Do not change the canonical format.
6. **Guide.** A Rust migration-set section: how to author a set, `status`/`plan`/`apply_next`, the lost-response procedure, drift and in-doubt handling, forward-only correction (no down migrations), the unsupported-server error. Find the Rust client docs home (`crates/client/shamir-client` docs or `docs/guide-docs/guide/`; confirm against the existing files, do not invent a new docs tree) and keep builder-only examples (no raw JSON).
7. **Tests** (CI-only; deterministic; the names of design §7.2 as the starting set): `rust_migration_set_uses_typed_ddl_builders_only`, `rust_migration_status_plan_apply_send_typed_admin_operations`, `rust_migration_lost_apply_response_queries_status_without_replay` (the scripted transport drops the response; assert exactly ONE apply was sent and the status query followed), `rust_migration_changed_checksum_or_gap_fails_before_apply` (assert nothing was sent), `rust_migration_body_canonical_vectors_match_file` (task item 5), an unsupported-server mapping test, and a real-server end-to-end test in `shamir-e2e` (boot the real server with a persistent store; apply two migrations in order, a repeat is a no-op, drift is refused before sending, status reports the applied prefix). Reuse the existing client test doubles/harness; read how `crates/client/shamir-client/tests/` and `shamir-e2e` build fixtures first.

## Do not

Change the canonical format, the typed model, the server handlers, the wire protocol or the Node/TypeScript clients; add a dependency; add a down/rollback or force-resolve API; retry an apply on any error; construct wire values by hand (builders only, `shamir-query-builder`); widen an existing item beyond what the new module needs (list every widening before doing it).

## Layout — plan it BEFORE coding (several folders are at the 7-entry limit)

`crates/client/shamir-client/src/` and `src/client/` both hold exactly 7 entries, so a new sibling is an eighth. Decide the home first: either a rename-only move of existing siblings into a new topical subfolder with re-exports keeping every public path (its own described change, git-detectable renames, no behaviour change), or a home inside an existing subfolder that has room. Count the entries of every folder you add to with `ls`; `python -I scripts/ci/check_layout.py` counts only TRACKED files, so check after the orchestrator's `git add` too. Every file at most 1000 lines, one primary item per file, `mod.rs` re-exports only, tests in `tests/` folders (no inline `#[cfg(test)]` modules), no local `use`, no new `#[allow]`.

## Test fixture checklist (every item failed in CI on earlier steps)

* Persistent stores only for the real-server test; keep every `TempDir` alive for the whole test; close every handle before reopening a directory; one runtime per test; handshakes not sleeps; every await bounded; a batch is at most 50 queries; distinct aliases.
* Tests that nest deep async frames (a real server plus the client) run on a roomy thread (`on_big_stack` pattern of the `shamir-db` schema-migration tests) or use the e2e harness's own runtime; `Box::pin` large awaits.
* Concurrent outcomes: assert on the set of outcomes, never on the join order.
