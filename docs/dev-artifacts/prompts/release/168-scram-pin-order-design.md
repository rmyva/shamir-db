# Brief: SCRAM-PIN-ORDER design (task #1988) - the client must verify the pinned server identity BEFORE it sends the SCRAM proof

You are session `sp-1`, a NEW executor in a fresh worktree (`<worktree>`, branch `scram-pin-design`) created from `origin/master`. This stage is DESIGN ONLY: one new document, no production code, no tests, no protocol change yet.

## Goal and why
Today the client sends its SCRAM client proof BEFORE it has verified the pinned server identity. In `crates/net/shamir-connect/src/client/handshake.rs` the pin (the hash of the server's Ed25519 identity key) is checked only when `auth_ok` arrives, after the proof is on the wire; TCP, IPC and WSS behave the same way (the admin-shell design says so). A rogue endpoint that completes the TLS or WebSocket upgrade and issues a valid challenge receives a proof it can attack offline (the TLS exporter binding stops replay on another connection; the password itself is never sent). The owner decided on 2026-11-26: CHANGE the protocol, before the first release (after the release every protocol change must stay compatible with deployed clients). This document is the design the change will be built from; an independent review of it follows before any code is written.
