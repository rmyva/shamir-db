## Goal and why
A transaction is bound to one repository when it begins. Today a later `TxExecute` step is not compared with that binding before it runs, and `tx_begin_as` resolves the repository by name more than once (before and after the open, with a comparison between them), so the repository the caller is told about can differ from the one the transaction is really open on if a rename or a re-creation lands in the window. The tests also do not isolate two properties: that a second transaction can take a key only after the first one ended, and that `CancelTx` verifies the identity of the transaction it cancels.

## Acceptance (three items)
1. **TxExecute checks the binding (12b).** Before a `TxExecute` step runs, compare the repository NAME it addresses with the repository the transaction is bound to; on a mismatch REFUSE the step with the existing typed refusal family (find how a wrong-repository request is refused elsewhere; do not invent a new wire error without need) AND roll the transaction back, so that no later step can run in it. A step that addresses the bound repository behaves exactly as today. `tx_handlers.rs` is at 795 lines: new logic goes into a NEW file with narrow members (members of new files that are `pub(crate)` or wider and not needed by a sibling are flagged by the CI rust-guard).
2. **`tx_begin_as` returns the repository the transaction is really open on (12c).** Make the facade return the repository handle on which the transaction was actually opened, remove the before/after comparison and the third lookup by name, and keep every observable behaviour (errors, ordering, the bound-repository identity used by item 1). All crates here are `publish = false`; keep the change to the minimum the contract needs and name every file and every changed signature in the report.
3. **The oracles (12e).** (a) A lock oracle: while the first transaction holds a key, a second transaction cannot take the same key (the existing typed outcome for a conflicting or blocked write); after the first one ended (commit or rollback) the second one CAN. (b) A separate `CancelTx` test with a SUBSTITUTED transaction (a transaction object whose identity differs from the one the request names) that isolates the identity check: the cancel must be refused or ignored as the code defines today and the other transaction must stay untouched; the test must fail if the identity comparison is removed (say how in a comment). (c) A test for item 1 (a mismatching step is refused and the transaction is rolled back; a following step on it fails) and one for item 2 (the returned repository is the one the transaction runs on, with a rename or re-creation injected into the former window through an existing test seam if one exists; if none exists, say so and test the contract at the level the code allows). Each test states in a comment which broken implementation it catches.
