## Goal and why
Review of the shutdown path (task #2032, read-only analysis, then spot-checked by the orchestrator) found five related weaknesses. None of them endangers data on disk: row locks live only in memory and the stores have their own file locks. 2. **One order of stopping (1b + 1c).** In `shutdown_with_budget` the repositories are flushed at stage 4 while the expired-transaction collector stops at stage 7, so a release can run after the flush. 4. **Bounded join of the scheduled backup (1e).** `join_schedule` is unbounded on purpose (cleanup order and owner lock), and it is unbounded in the binary too: after the overall deadline `drain` waits again without limit.
