## Findings to fix (in this order)

### 1. RFC 3339 fractional timestamps are corrupted (P1)
`crates/query/shamir-funclib/src/functions/datetime/core.rs` (around lines 515-528): the scanner finds `digit_count` but accumulates over `fractional.iter().take(9)`, i.e. including the zone suffix for short fractions, so the oracle's `.1Z` input yields 5200 ms instead of 100 ms; a non-digit byte below ASCII `0` can also underflow the subtraction (overflow-checked builds panic on VALID input). The offset match (around lines 531-549) is ASCII-only and rejects U+2212 (MINUS SIGN), which chrono accepts (`chrono-0.4.45` `src/format/parse.rs` around line 247, `src/format/scan.rs` around lines 236-243). Fix the fraction accumulation to the digit run only (up to the nanosecond precision chrono keeps), accept exactly what chrono accepts in the offset, and add table cases for 1, 2, 3, 6, 9 and 10+ digit fractions with `Z`, `+hh:mm` and U+2212 offsets.

### 2. `format` (strftime) output and pattern acceptance diverge (P1)
`%Z`: the code hard-codes `+00:00` (around line 420) but the locked chrono formats its UTC zone name as `UTC` (`chrono-0.4.45` `src/datetime/mod.rs` around line 1162, `src/format/formatting.rs` around lines 67 and 286, `src/offset/utc.rs` around lines 148-151): the oracle test itself (`datetime_tests.rs` around lines 717-725) already contradicts the implementation: decide from the chrono source what the function really returns for each timestamp type used by the registry and make code and oracle agree with chrono. Width and padding: the code (around lines 151-175, 317-344, 445-446) accepts arbitrary widths such as `%12d` and padding on composites such as `%_F`, while chrono does not support general widths and rejects padding on composite items (`chrono-0.4.45` `src/format/strftime.rs` around lines 473-485 and 614-638): mirror chrono exactly (the machine code `parse` for what chrono rejects). A width taken from a short query-supplied pattern must never drive an unbounded output allocation: pin a bound or reject, and test it.

### 3. Pattern PARSING still inherits jiff behaviour that differs (P1)
`core.rs` (around lines 681-691) forwards patterns to jiff. The oracle's `%#z` with an input `Z` is accepted by chrono but rejected by jiff's `%z` parser (`jiff-0.2.24` `src/fmt/strtime/parse.rs` around lines 89-94 and 421-431, configured `.zulu(false)`); signed expanded years cannot pass jiff's narrower civil type. Either configure jiff so the accepted language equals chrono's for every directive the whitelist admits, or implement the parse of the divergent directives yourself, or reject, with the SAME machine code chrono's outcome has, the inputs chrono would accept only if you can prove from the chrono source that no registered function can produce or receive them. For every directive of the whitelist, record in the report the accept/reject/value rule of chrono and what your implementation does (a table).

### 4. Local time on Windows is not preserved (P1)
`crates/foundation/shamir-types/Cargo.toml` line 28 enables only jiff's `tz-system`; `crates/foundation/shamir-types/src/entries/time.rs` (around lines 14-16) uses `Zoned::now()`. jiff's Windows implementation maps the OS zone to an IANA name through a database lookup and falls back to a UTC-like zone when the lookup fails (`jiff-0.2.24` `src/tz/system/windows/mod.rs` around lines 47-61, `src/tz/timezone.rs` around lines 325-335): with no bundled database a non-UTC Windows host can silently schedule in UTC (the scheduler uses `local_minute_of_day`). Prove the behaviour from the source, then fix with the smallest correct change: a jiff feature that bundles the database where the system one is absent (check `tzdb-bundle-platform` / `tzdb-bundle-always` semantics and the admission rules: a feature of a package version already in the base lock needs no exception; a NEW package would), or a direct OS call for the local offset that matches what chrono `Local` did. State the size and dependency trade-off. The existing test only compares against the ambient zone: a UTC runner cannot detect a regression. Add a test that cannot pass on a UTC-fallback (for example run the function under an explicit non-UTC zone through the jiff API and compare with the chrono oracle for a DST boundary) and say what CI would show.
